# ER 2 입력·출력과 하위 제어의 연결

기본 모델은 `gemini-robotics-er-2-preview`, Live 실험은 `gemini-robotics-er-2-streaming-preview`입니다. 모델 추론은 Google API에서, 물리·렌더링·하위 제어는 GPU 실습 호스트에서 실행합니다.

<a id="flow"></a>
## 1. 전체 구조

```text
사용자 목표 + 개발자가 정의한 도구 목록·규칙
                     ↓
Isaac Sim RGB ─→ ER 2의 관찰·판단 ─→ 함수 호출 또는 상태 보고
    ↑                                    ↓
새로운 물리 상태                    호스트가 호출·인자 검증
    ↑                                    ↓
물리 시뮬레이션 ← 관절 목표 ← 장면별 하위 제어기
                                         │
             ER 2 ← 실행 결과(completed/blocked/arrived 등)
```

두 피드백 루프가 있습니다.

- **작업 판단 루프:** RGB와 도구 실행 결과를 바탕으로 ER 2가 행동 선택·상태 판단·재판단을 수행합니다.
- **동작 제어 루프:** 하위 제어기가 로봇 관절·접촉·위치 등을 읽고 관절 목표를 반복 갱신합니다. 예를 들어 현재 서랍의 물리·제어 주기는 120 Hz입니다.

함수 호출 하나가 수십 초짜리 동작을 시작할 수 있습니다. 그동안 제어기는 계속 움직이며, 새 모델 출력은 다음 판단 시점에 발생합니다. 모델 출력 빈도와 제어기 갱신 빈도가 다릅니다.

Live 카메라는 계속 캡처하지만 API에는 `send_realtime_input(video=JPEG)`로 약 1.1초 이상의 간격으로 전송합니다. 네트워크와 처리 지연 때문에 실제 전송 간격은 더 길 수 있습니다. 카메라의 모든 렌더링 프레임이 API로 전달되는 것은 아닙니다. MP4는 기록·시청용이며 Live 입력으로 통째 전송하지 않습니다.

<a id="io"></a>
## 2. 실제 입력과 출력

ER 2가 받는 입력은 다음과 같습니다.

1. **RGB 이미지:** 기본 실습은 판단마다 한 장, Live 실습은 같은 세션으로 지속 전송하는 JPEG입니다.
2. **작업 지시와 heartbeat:** 목표, 지금 판단해야 하는 내용, 필요하면 관측 ID를 텍스트로 보냅니다. heartbeat는 호스트가 판단을 요청하는 메시지입니다.
3. **시스템 지시와 도구 정의:** 호출할 수 있는 함수 이름·설명·인자 형식, 한 판단에 한 도구 등의 제한입니다.
4. **대화 및 실행 결과:** 같은 세션의 이전 맥락과 도구의 완료·실패·차단 상태입니다. 기본 이미지 반복 실습은 이전 결과를 다음 프롬프트에 넣습니다.

모델에 깊이 지도, 정답 객체 좌표, 손가락 접촉력, 평가용 관절 로그를 보내지 않습니다. 이 정보는 로컬 제어·평가에서 사용합니다. 따라서 “모델은 RGB를 사용한다”는 말은 시각 입력에 대한 설명이며, 텍스트 지시·도구 결과도 함께 받습니다.

출력은 크게 두 가지입니다.

- **함수 호출:** `open_drawer()`, `navigate(route="right")`, `pick_place(...)`, `recover_pick_place(...)`처럼 등록된 행동 도구를 선택합니다.
- **텍스트 상태 보고:** `status`, `reason` 등의 JSON 형식으로 관찰한 상황을 설명합니다. Spot은 표시등 색상도 보고합니다. 도구 실행 뒤에는 짧은 확인 문장이 반환되기도 합니다.

함수 호출은 Google API가 로봇에 직접 명령을 전달하는 기능이 아닙니다. 호스트 프로그램이 응답을 받아 허용 함수·인자를 검사하고, `bridge()`를 통해 Isaac Sim 명령 대기열로 전달합니다. 허용 범위를 벗어난 호출은 거절합니다. 모델의 `goal_complete`와 평가기의 `task_success`도 별개입니다.

<a id="drawer"></a>
## 3. 서랍의 한 번의 호출과 여러 control 단계

서랍 열기 호출은 다음 형태입니다.

```json
{"function_calls": [{"name": "open_drawer", "args": {}}]}
```

서랍 도구에는 좌표 인자가 없습니다. 이 장면의 위 서랍을 여는 동작을 미리 구현했으며, ER 2는 실행할지 여부를 판단합니다.

```text
ER 2: open_drawer()
  ↓ 호스트 검증 → bridge("skill", skill="open_drawer")
DrawerMotion.begin()
  ↓
ungrip → lift → align → approach → grasp → pull
                                            ↓
                done ← settle ← retreat ← release
  ↓
호스트 → ER 2: {"controller_status": "completed"}
  ↓ 새 RGB + 다음 heartbeat
ER 2: {"status": "goal_complete", "reason": "..."}
```

`lift`는 안전 높이 이동, `align`은 손잡이 앞 정렬, `approach`는 손잡이 접근, `grasp`는 양쪽 접촉 확인, `pull`은 당기기, `release`는 놓기, `retreat`는 후퇴, `settle`은 안정화입니다.

이 단계들은 **직접 작성한 `DrawerMotion` 상태 머신**입니다. 목표 위치 오차·TCP 속도·접촉력·경과 시간 등을 검사해 다음 단계로 진행합니다. 각 단계의 목표 자세를 NVIDIA RMPFlow에 전달하고, 얻은 관절 목표에 속도 제한을 적용해 Franka를 구동합니다. 모델이 이 단계마다 `lift`나 `align`을 출력하지 않습니다.

손잡이 위치는 하위 제어기가 시뮬레이터에서 읽고 이 장면에 보정한 오프셋을 적용합니다. 이 도구는 해당 장면의 위 서랍에 맞춰져 있으며, ER 2는 좌표 대신 실행 여부를 결정합니다.

복구 실험에서는 첫 완료 보고 이후 실험 코드가 서랍을 닫습니다. 로봇이 후퇴했는지 확인한 뒤 서랍 관절 위치를 변경하는 테스트 이벤트입니다. 다음 영상과 heartbeat를 받은 ER 2가 `open_drawer()`를 다시 선택합니다.

서랍은 `BLOCKING` 도구입니다. 실행 중에도 JPEG 전송은 계속하지만 호스트는 도구 결과를 기다린 후 다음 판단을 요청합니다. 동작 중 ER 2가 모든 단계를 즉시 수정하거나 중단하는 방식까지 구현한 것은 아닙니다. 과속·비대상 서랍 이동 등 빠른 정지는 로컬 제어기가 담당합니다.

## 4. 픽앤플레이스와 로봇개의 차이

| 실험 | ER 2가 결정하는 것 | 로컬 코드가 담당하는 것 | 재판단 시점 |
|---|---|---|---|
| 기본 픽앤플레이스 | 집을 이미지 좌표·놓을 이미지 좌표, 다음 행동 여부 | 깊이·카메라 보정으로 3D 변환, 파지·운반·놓기 | 도구 종료 후 다음 이미지 |
| Live 픽앤플레이스 복구 | 동작 중 대상 이동·목적지 이동·낙하 보고, 복구 좌표 | 보고 수신 후 중단·관찰 자세 복귀, 좌표 검증과 재실행 | 초기 행동 중 감시 가능; 복구 도구 실행은 blocking |
| 서랍 | `open_drawer()` 선택, 열림 상태·완료 판단 | 손잡이 위치, 단계별 접근·접촉·당기기·후퇴 | 도구 종료 후 새 영상 |
| Spot 로봇개 | `center`/`right` 경로 선택, 표시등 판독 | 미리 정의한 경유점·자기 위치·속도 명령·보행·충돌 정지 | `blocked`/`arrived` 등 반환 후 새 영상 |

### 픽앤플레이스

함수 인자는 `pick`, `place`, `observation_id`입니다. 좌표 순서는 `[y,x]`, 범위는 `[0,1000]`입니다. 호스트는 관측 ID와 좌표를 검증하고, 해당 시점의 깊이 지도와 카메라 보정으로 두 픽셀을 3D 위치로 변환합니다. 알려진 블록 높이 5cm에 대한 보정도 적용합니다. NVIDIA Franka `PickPlaceController`에 이 위치를 주면 제어기가 관절 동작을 생성합니다.

Live 복구의 초기 행동은 일반 ER 2가 이미지 한 장으로 계획합니다. 별도의 ER 2 Streaming 세션이 초기 동작 중 RGB를 감시합니다. 모델이 `target_moved`, `goal_moved`, `grasp_failed`를 보고하면 **호스트가 정지와 관찰 자세 복귀를 실행**하고 같은 Live 세션에 복구를 요청합니다. 그때 모델이 `recover_pick_place(...)`의 새 좌표를 출력합니다. 중단 정책과 모드 전환 자체도 구현한 호스트 로직입니다.

이 감시는 저속 JPEG와 API 응답 지연을 포함하므로 안전 인증용 실시간 감시기로 해석하지 않습니다. 복구 도구가 실행되는 동안에는 결과를 기다립니다. 모든 움직임을 한 모델이 매 프레임 재계획하는 방식은 아닙니다.

### Spot

ER 2가 `navigate(route="center")` 또는 `navigate(route="right")`를 선택합니다. 경유점 좌표는 `scenario_rules.py`에 미리 정의했습니다. 로컬 경로 추종기가 시뮬레이터 위치와 방향을 읽고 전진·회전 속도를 계산하며, NVIDIA의 `SpotFlatTerrainPolicy`가 실제 보행 관절 동작을 생성합니다.

장애물 접근 시 빠른 정지는 로컬 레이캐스트 검사로 수행합니다. ER 2는 `blocked` 결과와 새 전방 영상으로 우회를 선택합니다. 도착 후에는 새 영상에서 표시등 색을 보고합니다. 새 지도의 SLAM이나 자유로운 경로 생성은 이 실험에 포함하지 않습니다.

카메라는 블록 실험의 고정 상부 RGB, 서랍의 고정 사선 RGB, Spot의 로봇 추종 전방 RGB입니다. Franka 손목 카메라로 수행한 실험이 아닙니다.

## 5. 영상의 각 표시 읽기

| 표시 | 실제 의미 |
|---|---|
| 왼쪽 시뮬레이션 영상 | 사람이 동작을 관찰하는 측면 카메라. 모델에 보내는 카메라와 다름 |
| `ACTUAL API INPUT` | 그 시점까지 실제 전송한 가장 최근 JPEG. 새 전송 전까지 유지 |
| `API REQUEST / latest heartbeat` | 호스트가 보낸 최근 판단 요청 텍스트. 전체 API 입력을 모두 보여주는 칸은 아님 |
| `API OUTPUT`의 `tool_call` | 모델이 요청한 함수 이름·인자. 허용되지 않은 호출은 호스트가 거절할 수 있음 |
| `API OUTPUT`의 `report` | 모델 텍스트를 파싱한 상태 보고. 화면의 `wall_time` 등은 호스트가 덧붙인 기록 메타데이터 |
| `API OUTPUT`의 `tool_result` | **제어기가 반환하여 호스트가 모델로 보내는 값. 모델 출력이 아님** |
| `control: lift/align/...` | 왼쪽 물리 영상에 대응하는 로컬 서랍 제어기의 현재 단계 |
| 맨 위 `OBSERVE/EXECUTING/VERIFY/...` | 호스트 실험 진행 모드. 로컬 제어 단계와 구분 |

`API OUTPUT` 칸에는 가장 최근의 `report`, `tool_call`, `tool_result`가 표시됩니다. `tool_result`는 제어기가 모델에 돌려주는 값입니다. 긴 원문은 화면에 일부만 표시되며 전체 내용은 로그에서 확인할 수 있습니다.

`control`은 API REQUEST 내용도 아닙니다. 위치가 요청 칸에 가까워 보이지만, 실제로는 왼쪽 영상 아래의 `evaluation_trace.jsonl` 기반 주석입니다. 이 문자열을 요청으로 보내지 않습니다.

예를 들어 모델이 `open_drawer()`를 한 번 호출한 다음 10초 동안 새 API 이벤트가 없으면 오른쪽 칸에는 같은 호출이 남아 있습니다. 그동안 로컬 제어기는 `lift → align → approach`로 움직일 수 있습니다. 새 모델 명령 없이도 한 스킬의 실행이 진행되는 것입니다. 완료 후에는 `tool_result`가 표시되고, 새 관찰을 요청한 뒤 모델의 완료 보고가 나타납니다.

통합 영상은 실행 뒤 실제 프레임·전송 시각·API 로그를 정렬한 재생본입니다. 새 추론이나 임의의 판단 자막을 생성하지 않습니다. 화면 오른쪽의 최신 JPEG가 특정 응답의 유일한 근거 프레임이라고 보장하지는 않습니다. Live 세션에는 이전 프레임·대화 맥락이 함께 있고 API 지연도 있습니다.

## 6. 직접 구현한 부분과 가져온 부분

| 계층 | 제공·구현 주체 |
|---|---|
| 이미지 이해·상태 보고·도구 호출 판단 | Google ER 2 / ER 2 Streaming 모델 |
| 도구 이름·설명·인자 schema, heartbeat, 호출 제한, 중단·재판단 흐름 | 이 프로젝트에서 직접 구현 |
| 이미지 좌표 검증·깊이의 3D 변환·Isaac Sim 연결 | 이 프로젝트에서 직접 구현, Isaac Sim 카메라 API 활용 |
| 블록 파지·운반 컨트롤러 | NVIDIA Franka `PickPlaceController` 활용, 장면·연결·종료 동작은 프로젝트 구현 |
| 서랍 단계·목표·접촉 확인·속도 제한 | `drawer_motion.py`에서 직접 구현 |
| 서랍의 목표 자세 → 관절 목표 | NVIDIA RMPFlow와 Franka 설정 활용 |
| Spot 경유점·경로 추종·충돌 정지 | 이 프로젝트에서 직접 구현 |
| Spot 보행 정책 | NVIDIA `SpotFlatTerrainPolicy` 활용 |
| 물리 접촉·센서·렌더링 | NVIDIA Isaac Sim |

도구들은 장면마다 제공한 소규모 스킬 인터페이스입니다. Google이 제공한 범용 로봇 스킬 라이브러리가 아닙니다. `lift`, `align`은 모델이 선택하는 최상위 스킬 목록이 아니라 `open_drawer` 내부 단계입니다.

## 7. 실제 원문 확인

서랍 실행 결과: `outputs/05_drawer/<실행_ID>/`

- `live_config.json`: 시스템 지시와 함수 정의
- `sent_frames/*.jpg`, `*.json`: 실제 전송 JPEG와 시각
- `turn_XX/prompt.txt`: heartbeat 텍스트
- `turn_XX/messages.json`: SDK가 수신한 실제 메시지 원문
- `turn_XX/response.txt`: 추출한 모델 텍스트
- `turn_XX/tool_result.json`: 실행한 도구와 로컬 결과
