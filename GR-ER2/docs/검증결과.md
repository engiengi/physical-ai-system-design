## 평가와 데이터의 의미

- `controller_status: completed`는 제어 시퀀스 종료입니다.
- `placement_within_tolerance`는 기하·속도·그리퍼 조건 검사입니다.
- `instruction_success`는 자동 판정하지 않습니다. 색상·대상·사용자 지시는 이미지와 함께 확인합니다.
- 평가용 물체 정답 좌표는 모델에게 제공하지 않습니다.
- 모델은 단계별 RGB 한 장을 받습니다. 전체 MP4는 동작을 확인하는 녹화 자료입니다.
- 움직임은 접촉 기반 시뮬레이션입니다. 방해 버튼의 위치 변경은 명시적으로 기록됩니다.
- 임의 물체·다른 크기·복잡한 장애물에 대한 파지는 검증 범위에 포함하지 않습니다.

원본 영상은 각 동작 폴더의 `input_video/camera.mp4`, `rollout_video/side.mp4`에 있습니다.

## 방해 후 재관찰·복구 — 2026-09-21

실제 실행: `outputs/03_perturbation_recovery/20260921_123657_e59c4552/`

이 기본 복구 실험의 카메라는 `/World/TopCamera` 고정 상부 RGB-D 카메라입니다. ER 2에는 각 판단마다 RGB 한 장을 전달하고 깊이는 로봇 제어기에만 전달합니다. 추가 Live 스트리밍 실험은 아래 별도 항목에 기록합니다. 로봇팔 부착 카메라와 연속 관절 시각 서보는 구현 범위에 포함하지 않습니다.

기준 조건에서는 API 판단 1회, 방해 조건에서는 3회가 이루어졌습니다.

| 항목 | 방해 없음 | 첫 동작 1초 후 빨간 블록 이동 |
|---|---|---|
| 초기 장면 | scene 0 | 동일 scene 0 |
| 첫 집기 좌표 `[y,x]` | `[575,665]` | `[575,665]` |
| 첫 행동 배치 | 성공 | 실패, 빨간 블록이 트레이 밖에 남음 |
| 다음 집기 좌표 | 추가 행동 없음 | 새 이미지에서 `[356,720]` 선택 |
| 두 번째 행동 | 없음 | 빨간 블록 배치 성공, 목적지 XY 오차 약 17.9 mm |
| 마지막 모델 판단 | 판단 횟수 1회로 종료 | 세 번째 관찰에서 트레이 내부 확인 후 추가 함수 호출 없이 완료 응답 |
| 전체 관찰 영상 | 26.9초 / 269프레임 | 56.7초 / 567프레임 |
| 복구 판정 | 해당 없음 | `recovery_observed: true` |

두 전체 영상은 10 FPS, 시뮬레이션 시간 기준입니다. 실제 경과 시간은 각각 약 33.9초, 72.6초입니다. 모델 대기 시간과 방해 시점도 녹화했습니다.

복구 조건의 첫 제어 시퀀스는 원래 위치를 향해 진행했습니다. 이후 모델은 새 이미지와 이전 행동·제어기 종료 상태를 받아 집기 좌표를 바꿨습니다. 방해의 정답 위치나 평가용 물체 좌표는 모델에 제공하지 않았습니다.

최종 이미지에서도 빨간 블록의 트레이 배치를 확인했습니다. 다만 복구 동작 중 **파란 블록이 약 3.6 cm 이동**한 부수적 변화가 평가 기록과 이미지에 나타납니다. 빨간 블록 복구 성공과 충돌 없는 조작 능력은 별개로 해석합니다. 조건당 한 회의 사례이며 일반적 복구 성공률을 측정하지 않았습니다.

자료:

- 실험 폴더의 `README.md`: 조건별 영상·이미지·응답 링크.
- `perturbed/input_video/camera.mp4`, `perturbed/rollout_video/side.mp4`: 전체 방해·재관찰·복구 영상.

- `perturbed/actions/step_02/metrics.json`: 복구 배치와 부수적인 물체 위치 변화.

## Live 카메라 스트리밍 감독·복구 — 2026-09-21

실행 폴더: `outputs/04_streaming_recovery/20260921_125851_1a4b63dc/`

일반 ER 2가 첫 집기 행동을 계획하고, 별도의 `gemini-robotics-er-2-streaming-preview` Live API 세션이 동작 중 카메라를 감독했습니다. JPEG를 1.1초 이상의 간격으로 전송하고, 앞선 턴이 완료된 뒤 heartbeat 텍스트를 전달했습니다. 모델에 방해 시점이나 정답 이동 좌표는 알리지 않았습니다. 실제 물리 복구 도구는 `BLOCKING`으로 실행했습니다.

| 항목 | 실제 확인 결과 |
|---|---|
| 전송 | 지속 WebSocket 세션, 실제 카메라 JPEG 39장 |
| 판단 | 기준 장면 확인 → 변화 없음 → 목표 이동 감지 → 복구 행동 → 완료 확인, 총 5개 턴 |
| 방해 후 감지 지연 | 약 5.85초, 호스트 수신 시각 기준 |
| 첫 행동 중단 | `interrupted_by_stream_monitor`, 행동 시작 후 5.6초(시뮬레이션 시간)에 종료 |
| 중단 후 처리 | 현재 관절 목표 유지 → 2초 관찰 자세 복귀, 물체 초기화 없음 |
| 복구 | 같은 Live 세션이 새 좌표로 집기·배치. 목적지 XY 오차 약 19.6 mm |
| 마지막 판단 | Live 모델 `goal_complete`, 평가·최종 이미지에서도 트레이 배치 확인 |
| 종합 판정 | `streaming_recovery_observed: true` |
| 전체 영상 | 39.3초 / 393프레임 / 10 FPS, 실제 경과 약 51.2초 |

복구 중 파란 블록도 약 2.7 cm 이동했습니다. 목표 복구와 충돌 없는 조작은 별개로 검토해야 합니다. 일반 ER 2와 Live 모델이 함께 사용됐으므로 기존 6.4절 대비 성능 향상을 정량 주장할 수 없습니다.

## Brev L40S API·Live 복구 실험 — 2026-09-28

같은 사양의 새 L40S 서버에서 Gemini API를 연결했습니다. 이미지 비교, Franka 블록 배치, Live 대상 이동 감지·복구를 실행했습니다.

### 실행 결과

결과 폴더는 `outputs/` 기준입니다.

| 점검 | 실제 결과 | 결과 경로 |
|---|---|---|

### Live 복구 결과

- 일반 ER 2가 초기 집기를 제안하고, 별도의 Live 세션이 지속 입력을 받아 이동을 감지했습니다. 감지 후 중단·관찰 자세 복귀·Live의 새 좌표 도구 호출로 복구했습니다.
- `interrupted_while_action_active=true`, `streaming_recovery_observed=true`, `final_task_succeeded=true`, `run_error=null`입니다. 복구 후 요청 위치 오차는 약 4.8mm입니다.
- 첫 복구가 끝난 뒤 모델은 아직 운반 중이라고 판단했습니다. 다음 턴에 트레이 안의 블록을 다시 집도록 요청했지만, 하위 제어가 놓을 위치 검사를 통해 거부했습니다. 마지막 관측에서는 완료를 보고했습니다. 실제 실행된 복구 동작은 1회이며 추가 요청의 오류는 `02_isaac_sim/20260927_153557_a111d035/error.json`에 남았습니다.
- 한 장면·한 조건에서 1회 실행한 결과입니다. Brev에서 서랍·Spot·협업·사후 영상 평가의 API 실험은 수행하지 않았습니다.
- `placement_within_tolerance`는 제어 목표 위치 평가입니다. 기본 동작의 일반 지시 성공률을 자동으로 측정한 것은 아니며, 입력·최종 이미지에서 빨간 블록이 트레이 안에 있는지도 확인했습니다.
