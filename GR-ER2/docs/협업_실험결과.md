원문과 실제 입력 영상은 각 실행의 `video_progress/`에서 확인합니다. [공식 영상 진행률·완료 시점 문서](https://ai.google.dev/gemini-api/docs/robotics-video-progress)의 인터페이스를 참고한 커스텀 검증입니다.

## 2. Franka–Spot–Franka — 자재 운송과 복구

기존 두 Spot 점검 실험을 폐기하고, 두 Franka와 Spot 한 대가 물체를 실제로 인계하는 실험으로 교체했습니다. [실행방법 6.10절](../실행방법.md#transport), [설계·역할·단순화](자재운송_실험설계.md)를 먼저 확인합니다.

> ER 2가 A의 적재 결과를 확인하고 Spot을 출발시킨 뒤, B의 현장 카메라를 보고 하역을 지시한다. 적재 실패에는 재시도, 통로 차단에는 관찰과 우회를 선택한다.

- 정상: A 적재 → 새 이미지로 적재·팔 복귀 확인 → Spot 직선 이동 → B 카메라 요청 → B 하역 → 최종 이미지로 완료 확인.
- 적재 실패: 첫 A 동작에서 손가락을 열린 상태로 유지했습니다. ER 2가 두 번째 집기를 지시하고 적재를 확인한 뒤 Spot을 출발시켰습니다. 하역 호출에 불필요한 `destination` 인자를 넣어 한 번 거부됐지만, 모델이 인자를 고쳐 다시 호출했습니다. 이 거부는 물리 동작 횟수에 포함하지 않습니다.
- 통로 장애: Spot 출발 후 직선 통로에 실제 충돌체를 삽입했습니다. 로컬 제어가 `blocked`를 반환한 뒤 ER 2가 `observe(camera_id="Spot")`를 호출했습니다. 다음 판단에서 모델이 `route="detour"`를 선택했고, 자재를 유지한 채 B에 도착해 하역했습니다.

로봇 세 대의 동작은 인계 순서에 따라 진행되며 동시 실행 구간은 0초입니다. 이 실험에서 확인하는 협업은 서로 다른 역할의 연결, 인계 확인, 작업 재개 조건의 판단입니다. 중앙 모델 한 개가 세 로봇을 조율합니다.

## 해석 범위와 원고에 쓸 결론

**“ER 2가 카메라 관찰과 비동기 도구 응답을 연결해, 서로 다른 로봇의 인계 순서를 진행하고 적재 실패·통로 차단 이후 작업을 재개하는 사례를 확인했다.”**

역할과 지도, 도구 종류는 사전에 주어집니다. 팔의 조작은 공식 PickPlaceController/RMPFlow와 깊이 보정, Spot의 보행은 공식 정책과 자기 위치·경유점 제어가 담당합니다. 이 결과로 로봇의 관절 제어를 ER 2가 학습했다거나 미지 환경의 임의 작업을 해결한다고 주장하지 않습니다.

컨베이어는 인계 위치에서 정지한 구성입니다. 움직이는 벨트에서 자재를 추적해 집는 실험, 실제 하드웨어, 산업 현장의 안전 인증은 포함하지 않습니다. Spot 적재함과 카메라의 단순화는 설계 문서에 정리했습니다.

조건별 개별 사례이며 일반 성공률이나 ER 1 대비 우위를 주장하지 않습니다. `outputs/`는 Git 제외 대상이며 Spark와 워크스테이션에 보관합니다.

## 최종 검증

- 자동 테스트 57개, Python 구문 검사, 셸 구문 검사를 통과했습니다.
- 새 모델 실험 세 조건의 MP4 148개를 모두 디코딩했습니다. 원본·통합·개별 관측 clip·진행률 평가 영상이 포함됩니다.
- 녹화 시점 1,408개의 프레임·시간·평가 기록을 대조했고, API 요청보다 미래인 관측은 없었습니다.
- 실제 사용한 깊이 원본으로 집기 중심 보정 7회를 재계산해 기록과 일치함을 확인했습니다.
- Spark 직접 GUI를 확인하고 API 없는 보행 시험을 통과했습니다. 최종적으로 시뮬레이터와 API 실행 프로세스를 종료했습니다.
