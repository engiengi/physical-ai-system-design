## 1. 기획 의도와 전달할 질문

### 제목 후보

**Gemini Robotics ER 2는 여러 로봇을 어떻게 협업시킬까? — 시각적 판단·다단계 도구·실패 복구**

부제: 이미지 좌표에서 두 로봇팔의 키트 준비, 로봇개의 자재 운송, 영상 진행 상태 판단까지.

### 한 문장 메시지

> ER 2가 관찰과 도구 실행 결과를 이용해 여러 로봇의 작업 순서와 복구 행동을 선택하는 과정을 확인하고, 모델의 완료 판단을 실제 물리 상태와 대조한다.

독자가 답을 얻어야 할 질문:

1. 모델은 이미지에서 무엇을 출력하는가?
2. 이미지 좌표나 함수 호출이 어떻게 실제 로봇 움직임으로 이어지는가?
3. 작업 중 대상·목표·파지 상태가 바뀌면 무엇이 다시 판단하고 무엇이 복구를 실행하는가?
4. 같은 구조를 서랍과 로봇개에 적용할 때 어떤 부분을 새로 구현해야 하는가?
5. 어디까지가 모델의 능력이고 어디부터가 준비된 제어기와 시뮬레이터의 도움인가?
6. 여러 로봇의 작업 분배·인계·재시도를 실제 도구 호출에서 확인할 수 있는가?
7. 영상에서 판단한 진행률·완료 여부·완료 시각은 실제 기록과 얼마나 일치하는가?

성격은 연결 구조와 개별 동작 사례를 보여주는 구현 실습이다. 반복 성공률·모델 우열·실물 안전성을 입증하는 벤치마크는 수행하지 않았다. `GR-ER2`는 프로젝트 폴더명이며 모델 표기는 Gemini Robotics ER 2로 통일한다.

## 2. 권장 원고 구성

본문 중심은 E8~E10의 다단계 도구 사용·멀티로봇 협업·영상 진행 판단이다. E1~E3은 연결 구조를 이해하는 도입으로, E4~E7은 선택 심화 자료로 활용한다. 아래 순서는 편집안이며 모든 실험 영상을 통째로 넣을 필요는 없다.

| 원고 절 | 이야기와 화면 | 연결할 실행방법 |
|---|---|---|
| 1. 질문 제시 | A 적재 → Spot 운반 → B 하역 장면. “누가 다음 로봇을 출발시키고 실패 뒤 무엇을 다시 확인할까?” | 0절의 전체 순서 |
| 2. 판단과 제어의 구조 | RGB·지시 → 모델 호출 → 호스트 검증 → 하위 제어 → 새 관찰 | 0절, 역할 설명 문서 |
| 3. 이미지에서 공간 출력 확인 | E1 두 모델의 실제 좌표·오버레이. 유사한 결과도 그대로 제시 | 4절 |
| 4. 좌표에서 실제 동작으로 | 수동 점검 → E2 한 블록 → E3 세 블록 | 5절 → 6.1 → 6.2 |
| 5. 장면이 바뀌면 | E4를 짧게 설명하거나 생략. E5 S1·S3 중심, S2는 해석 주의 사례 | 선택 6.4, 본 실습 6.5 probe → 6.6 |
| 6. 서랍으로 확장 | E6 최신 동작 영상과 control 단계. 특권 상태를 명시 | 6.7 |
| 7. 로봇개로 확장 | E7 중앙 차단 → 우회 → 빨간 표시등 | 6.8 |
| 8. 두 팔의 협업 | E8 동시 작업·중앙 전달·재시도, 실제 배치와 완료 주장의 불일치 | 6.9 |
| 9. 서로 다른 로봇의 인계 | E9 정상 운송·적재 실패·장애물 우회. 실제 API 선택과 물리 결과 연결 | 6.10 |
| 10. 영상으로 완료를 판단할 수 있을까 | E10 진행률과 완료 시각을 따로 평가. 성공·오판 함께 제시 | 6.11 |
| 11. 결과의 의미 | 모델 판단과 제어 성능, 실제 센서로 대체할 부분, 사례 연구의 한계 | 8절 자료 확인 → 9절 종료 |

원고 내 실습 안내 예: “직접 실행하려면 실행방법 6.7절에서 제어기 점검을 먼저 수행하고, 품질 검사 통과 후 본 실험 명령을 실행하세요.” 설치 명령 전체를 원고에 복제하지 않는다. 링크는 [실행방법](실행방법.md)의 해당 앵커를 사용한다.

## 3. 공통 실험 환경과 역할

| 항목 | 실제 사용 |
|---|---|
| 시뮬레이션 장비 | DGX Spark / GB10 / ARM64 / 드라이버 580.159.03 |
| Isaac Sim | `nvcr.io/nvidia/isaac-sim:6.0.0-dev2` |
| API 호스트 환경 | Python 3.12.3 / google-genai 2.24.0 |
| 이미지·일반 행동 모델 | `gemini-robotics-er-2-preview` |
| 동일 이미지 비교 모델 | `gemini-3.5-flash` |
| Live 모델 | `gemini-robotics-er-2-streaming-preview` |
| 모델 실행 위치 | Google API. Spark에 ER 2 가중치를 내려받아 실행하지 않음 |
| 시각 입력 | 블록: 고정 상부 RGB / 서랍: 고정 사선 RGB / Spot: 로봇 추종 전방 RGB |
| Live 전송 | 지속 세션에 JPEG, 전송 사이 최소 약 1.1초. 처리 지연 포함 시 더 느릴 수 있음 |
| 기본·Live 실험 영상 | 원본 카메라 10 FPS·시뮬레이션 시간, 통합 영상은 실제 경과 시간 정렬 |
| E8·E9 협업 영상 | 원본 5 FPS·통합 2.5 FPS, 동일한 시뮬레이션 시간축 |
| E8·E9 모델 입력 | 일반 ER 2 Interactions API. E8은 이미지, E9는 로컬 카메라 이미지와 직전 영상 구간 |
| E10 영상 평가 | 중간·최종 시점까지의 전체 관찰 영상, 1 FPS 샘플링. 작업 제어와 별도 호출 |

기본 블록 실험은 판단마다 RGB 한 장을 제공한다. Live 블록 복구는 일반 ER 2의 초기 계획 + 별도 Streaming 세션의 감독·복구라는 혼합 구성이다. 서랍·Spot은 Live 세션으로 도구 선택·결과 확인을 수행한다.

```text
지시 + 도구 정의 + RGB + 이전 도구 결과
                    ↓
             ER 2 관찰·판단
                    ↓
         함수 호출 / 텍스트 상태 보고
                    ↓
          호스트 검증·실행·복구 흐름
                    ↓
             장면별 하위 제어
                    ↓
             실제 물리 상태 변화
                    ↓
             새 RGB·결과 피드백
```

하위 제어에는 별도의 수치 피드백 루프가 있다. 관절·깊이·접촉력·정답 위치를 활용하는 범위는 실험마다 다르며 모델 입력과 분리해 설명한다. 자세한 설명은 [폐루프 구성](docs/폐루프_구성과_모델_제어기_역할.md)과 [운송 실험 설계](docs/자재운송_실험설계.md)를 참고한다.

위 하드웨어는 실제 검증 장비다. ER 2 자체는 Google API에서 실행한다. 시뮬레이션 하드웨어를 바꾼 경우 이 기록만으로 해당 장비에서의 성능·설치 호환성이 검증됐다고 표기하지 않는다.

아래 결과는 기록된 개별 실행이다. 최신 코드로 재실행할 때 출력·호출 횟수·오차가 동일하다고 보장하지 않는다. 실행별 당시 지시·설정·코드 해시는 각 폴더에 보존돼 있다.

### E1. 동일 이미지에서 두 모델은 무엇을 출력하는가

**의도:** 자연어 지시와 이미지 영역이 좌표로 연결되는 형식을 이해한다. 일반 모델도 가능한지 같은 입력으로 확인한다.

**설계:** 동일한 Isaac Sim RGB 이미지에서 빨간 블록과 녹색 트레이를 지시하고 두 모델의 `[y,x]` 정규화 좌표·원문·오버레이를 나란히 비교한다.

**실제 결과:**

| 객체 | ER 2 | Gemini 3.5 Flash |
|---|---|---|
| 빨간 블록 | `[575,664]` | `[575,664]` |
| 녹색 트레이 | `[472,306]` | `[475,305]` |

이 사례에서는 매우 유사한 점을 출력했다. 수작업 정답 주석이나 반복 정확도 평가가 없으므로 ER 2가 더 정확하다는 결론을 내리지 않는다. Bounding Box·관계·텍스트 계획·2D 경로는 실행 가능한 추가 기능이며, 이 대표 결과에 모두 실행된 것으로 묶지 않는다.

### E2. 이미지 좌표를 실제 파지로 연결하기

**의도:** pointing과 실제 로봇 제어 사이에 필요한 변환·검증 과정을 보여준다.

**설계:** 먼저 5절의 수동 클릭으로 제어 경로를 확인한다. 이후 ER 2에 빨간 블록을 트레이로 옮기도록 지시한다. `pick_place(pick, place, observation_id)`를 검증하고, 해당 관측의 깊이·카메라 보정으로 3D 좌표를 얻어 NVIDIA Franka PickPlaceController에 전달한다. 알려진 5cm 블록 높이를 사용한다.

**실제 결과:** 요청 목적지 대비 최종 블록 XY 오차 약 **6.4mm**, `placement_within_tolerance: true`. 이는 모델의 2D 인식 오차가 아니라 요청한 배치점에 대한 최종 물리 위치 오차다.

**자료:**

- [입력 카메라 원본](outputs/02_isaac_sim/20260921_092010_c02a0349/input_video/camera.mp4)
- [로봇 동작](outputs/02_isaac_sim/20260921_092010_c02a0349/rollout_video/side.mp4)

<a id="e3"></a>
### E3. 새 관찰로 블록 세 개 옮기기

**의도:** 행동 후 달라진 장면을 다시 보고 다음 대상을 선택하는 기본 폐루프를 확인한다.

**설계:** 세 블록을 트레이의 빈 위치로 옮기도록 요청한다. 한 관측에 한 번의 함수 호출을 허용하고, 다음 호출 전에 새 RGB를 제공한다.

**실제 결과:** 노랑 → 파랑 → 빨강 순서로 세 동작 수행. 요청 목적지 XY 오차 약 **11.0 / 3.0 / 10.5mm**, 세 배치 모두 허용 오차 통과. 행동 횟수 제한 도달과 모델의 완료 선언은 구분한다.

- [노랑 동작](outputs/02_isaac_sim/20260921_092646_1c381852/rollout_video/side.mp4)
- [파랑 동작](outputs/02_isaac_sim/20260921_092723_ec5412d5/rollout_video/side.mp4)

동작별 폴더의 `input_video/camera.mp4`, `metrics.json`도 사용한다. 세 동작을 한 파일로 묶은 공식 기록이라고 표현하지 않는다. 편집으로 연결할 경우 각 행동 경계를 표시한다.

**실습 연결:** 6.2. 여러 물체 배치는 ER 2로 실행한 사례이며 Flash와의 로봇 성능 비교는 없다.

<a id="e4"></a>
### E4. 동작 후 재관찰 복구 — 선택 설명

**의도:** 행동이 끝난 다음 새 이미지를 받는 구성과, 행동 중 감시하는 Live 구성의 차이를 소개한다.

**설계:** 기준 조건과 첫 행동 60tick(시뮬레이션 1초) 후 빨간 블록을 이동시키는 조건을 한 번씩 실행한다. 첫 행동은 원래 목표로 계속 움직이고, 끝난 뒤 다시 관찰한다.

<a id="e9"></a>
### E9. Franka–Spot–Franka 자재 운송과 복구

**의도:** 서로 다른 로봇의 역할·인계 순서와 예외 대응을 한 작업 안에서 보여준다. A가 적재에 실패했을 때 Spot의 출발을 미루는지, 길이 막힌 뒤 새 카메라를 보고 경로를 다시 선택하는지가 핵심이다.

**환경:** 떨어진 두 컨베이어 작업장에 Franka A/B를 두고 Spot 한 대가 사이를 이동한다. A가 5cm·0.05kg 자재를 Spot 적재함에 놓고, Spot이 B로 운반하며, B가 자재를 꺼내 지지면에 배치한다. **컨베이어는 인계 위치에서 정지한다.** 벨트 구동·움직이는 자재 추적은 이번 구현 범위에 없다. 자재는 동적 물리 물체이며 적재 이후 순간 이동이나 강제 부착 없이 운반된다.

```text
A 카메라 확인 → A 적재 → 적재·팔 복귀 확인 → Spot 출발
                                                   ↓
                              통로 차단 → 전방 재관찰 → 우회 선택
                                                   ↓
B 도착 → B 카메라 확인 → B 하역 → 새 관측으로 완료 판단
```

**역할 구분:**

## 5. 영상 화면·API·control 설명

E5~E7의 기존 Live 통합 영상이 나올 때 다음을 짧게 설명한다.

| 화면 | 의미 |
|---|---|
| 왼쪽 물리 영상 | 시청자용 측면 카메라 |
| 오른쪽 ACTUAL API INPUT | 그 시점까지 실제 전송한 최신 JPEG |
| API REQUEST | 최근 heartbeat. 시스템 지시·도구 정의·이전 맥락은 별도 로그에 있음 |
| API OUTPUT의 tool_call/report | 모델의 호출·보고. report에 붙은 기록 시각 등은 호스트 메타데이터 |
| API OUTPUT의 tool_result | 로컬 제어기가 모델에 반환하는 값. 모델 생성 출력과 구분 |
| control: lift/align 등 | 로컬 서랍 상태 머신 단계. 모델의 연속 명령이 아님 |

현재 영상 제목은 모델 출력과 도구 결과를 같은 칸에 묶는다. 원고·편집 자막에서 발신자를 구분한다. 기존 영상의 제목이 완전히 수정된 것으로 쓰지 않는다.

`open_drawer()` 한 번을 화면에 유지하는 동안 제어기는 여러 단계를 진행한다. 새로운 API 이벤트가 없으면 출력 칸은 그대로이고 control만 바뀔 수 있다. 오른쪽 최신 JPEG가 해당 응답의 유일한 근거라고 주장하지 않는다. 모델에는 이전 프레임·대화 맥락도 있다.

E8·E9의 협업 통합 영상은 API 입력·출력, `LOCAL` 작업/제어 단계, `EVALUATOR` 진행 상태를 나눠 표시한다. 운송의 overview는 시청자용 전체 장면이다. API 입력 패널은 실제 제출된 이미지이며 영상 구간의 원본은 별도로 저장돼 있다. 평가용 단계나 로컬 제어 단계가 바뀌었다고 모델이 새 명령을 낸 것으로 읽지 않는다. E9는 일반 Interactions API에 이미지·짧은 과거 영상을 반복 제출하는 구성이다.

## 6. 화면 구성과 편집 순서

1. **도입:** A 적재·Spot 운반·B 하역의 4장 비교와 통합 영상으로 전체 목표부터 보여준다.
2. **구조:** 이 문서의 흐름을 편집 도식으로 옮긴다. 새 개념 그림은 아직 별도 이미지 파일로 제작하지 않았다.
3. **좌표:** E1 공통 입력 → 두 오버레이. 좌표 순서·범위를 표시한다.
4. **연결:** E2의 호출 인자와 실제 동작, E3의 각 행동 전 새 관측을 연결한다.
5. **변화:** S1 통합 영상의 이동·보고·중단·재파지, S3의 낙하·좌표 거절·수정을 본문 중심으로 쓴다.
6. **해석:** S2는 복구 전 이미 트레이 안에 있는 프레임을 먼저 보여주고 목적지 감지 사례로 설명한다.
7. **서랍:** 최신 영상과 파지·놓기·후퇴 사진, 품질 그래프. `open_drawer`와 control 단계의 차이를 설명한다.
8. **Spot:** 중앙 막힘·우회 선택·도착·표시등 사진. 로컬 정지와 모델의 경로 선택을 구분한다.
9. **협업:** E8 두 팔 동시 작업과 전달 실패 후 재시도. 최종 트레이 밖 블록과 완료 주장을 같이 표시한다.
10. **인계·복구:** E9 정상 흐름을 먼저 보여주고 적재 실패의 재파지, 장애물의 `blocked` → 전방 관찰 → `detour`를 이어 붙인다. 모델 출력과 로컬 제어의 발신자를 자막으로 구분한다.
11. **영상 판단:** E10 중간·최종 입력과 응답·실제 구간을 비교한다. 완료 시각 오류와 중간 진행률 과대 판단을 포함한다.
12. **결론:** 작업 판단·실행·평가의 세 역할과 실물에서 추가할 센서·추정 과제를 정리한다.

속도를 변경하거나 대기 구간을 줄이면 자막으로 표시한다. 원본 입력 영상·전송 JPEG·모델 응답·평가 수치를 편집본과 함께 보관한다. 성공 장면만 보여주며 좌표 거절이나 부수적 물체 이동을 숨기지 않는다.

## 7. 결론·한계·금지할 과장

### 근거가 있는 결론

- 실제 API 출력의 이미지 좌표와 함수 호출을 물리 시뮬레이션에 연결했다.
- 새 관찰로 다음 물체·변화된 위치·제공된 우회 경로를 선택한 사례를 확인했다.
- 모델의 판단과 별개로 하위 제어·좌표 검증·접촉 검사·종료 평가가 필요했다.
