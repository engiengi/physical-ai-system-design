## 0. 실습 선택과 준비물

| 경로 | 필요한 장비 | 할 수 있는 실습 |
|---|---|---|
| API 이미지 실습 | Ubuntu 24.04 PC, 인터넷, Google 계정 | 내 이미지 업로드 → ER 2 / 일반 Gemini 비교. NVIDIA GPU·Docker 불필요 |
| 워크스테이션 | Ubuntu 24.04 NVIDIA RTX 워크스테이션 | [1.1~1.7 설치](#host-os) → [2 API](#step-2) → [3 실행](#step-3). 직접 모니터는 [7.3](#gui-local) |
| Brev 클라우드 | GPU 없는 개인 PC + Brev L40S 서버 | [1.8 계정·생성](#brev-setup) → [1.9 설치](#brev-install) → [2 API](#step-2) → [7.5 GUI 실행](#brev-gui). 같은 로봇 실습 사용 |

워크스테이션 설치는 **Ubuntu 24.04 LTS / Python 3.12 / Bash** 기준입니다. Brev는 **Ubuntu 22.04.5 / 별도 설치한 Python 3.12.11** 기준입니다. Windows/macOS의 GPU 없는 PC도 Brev에 SSH 접속하고 브라우저로 조작할 수 있습니다. Windows 명령은 WSL Ubuntu 터미널에서 실행합니다. WSL에는 SSH 도구만 설치하며 시뮬레이터는 Brev에서 실행합니다.

시뮬레이션 호스트는 NVIDIA 공식 x86_64 기준 **RAM 32GB 이상, RTX 4080·VRAM 16GB급 이상**을 확인하세요. 여러 로봇·카메라 실험에는 여유 메모리가 필요합니다. 설치·컨테이너·영상 저장을 위해 **SSD 여유 100GB 이상**을 권장합니다. GPU에 RT Core가 필요하며 A100/H100은 지원 대상에서 제외됩니다. 일반 ARM PC는 이 경로의 지원 대상이 아닙니다. [NVIDIA 요구사항](https://docs.isaacsim.omniverse.nvidia.com/6.0.0/installation/requirements.html)

| 항목 | 이 코드가 사용하는 버전 |
|---|---|
| 호스트 Python | 3.12 |
| Google SDK | `google-genai==2.24.0` |
| 이미지·수치 패키지 | `Pillow==11.3.0`, `numpy==2.2.6` |
| 나머지 Python 의존성 | `constraints.txt`에 고정 |
| Isaac Sim | `nvcr.io/nvidia/isaac-sim:6.0.0-dev2`, 컨테이너 내장 Python |
| 일반 ER 2 / 비교 모델 | `gemini-robotics-er-2-preview` / `gemini-3.5-flash` |
| Live 전용 모델 | `gemini-robotics-er-2-streaming-preview` |

ER 2 추론은 Google API에서 실행합니다. GPU는 시뮬레이션의 렌더링·물리·하위 제어에 사용합니다. API 비용과 서버 대여 비용은 별도이며, Preview 모델 접근 권한·이름·요금은 달라질 수 있습니다. 모델을 자동 대체하지 않습니다. [공식 ER 2 안내](https://ai.google.dev/gemini-api/docs/robotics-overview)

<a id="host-os"></a>
### 1.1 OS와 기본 도구

새 컴퓨터는 [Ubuntu 24.04 LTS](https://releases.ubuntu.com/24.04/)를 설치하고 로그인합니다. 디스크 설치는 기존 자료를 백업한 뒤 진행하세요. 아래 명령부터는 Ubuntu 터미널에서 실행합니다.

원격 GPU 서버를 사용할 때만 개인 PC에서 접속합니다. 이미 서버 터미널이면 다시 SSH하지 않습니다.

**실행 위치: 개인 PC · 원격 서버를 사용할 때만 · 서버 관리자가 제공한 계정·주소 입력**

```bash
read -r -p "SSH 접속 대상 (예: ubuntu@서버주소 또는 SSH 별칭): " GR_ER2_HOST
ssh "$GR_ER2_HOST"
```

**실행 위치: 실습 호스트 · 최초 1회 · Ubuntu 24.04**

```bash
cat /etc/os-release
uname -m
sudo apt-get update
sudo apt-get install -y git gh curl ca-certificates gnupg rsync \
  python3.12 python3.12-venv ffmpeg tmux fonts-dejavu-core xauth
python3.12 --version
ffmpeg -version
```

Ubuntu 22.04 기본 Python 3.10으로 설치하지 마세요. 이 매뉴얼은 24.04의 Python 3.12로 버전을 통일합니다. 호스트에 PyTorch·CUDA Toolkit·Isaac Lab을 별도로 설치할 필요는 없습니다.

<a id="clone"></a>
### 1.2 저장소 받기

배포 저장소는 [physical-ai-system-design](https://github.com/engiengi/physical-ai-system-design)입니다. 비공개로 제공받은 경우 먼저 GitHub 초대를 수락하고 아래 인증을 진행합니다. 공개 접근이 가능하면 인증 블록은 생략합니다.

**실행 위치: 실습 호스트 · 비공개 저장소 접근이 필요한 경우 최초 1회**

기본 경로는 `$HOME/physical-ai-system-design/GR-ER2`입니다. 다른 위치에 복제했다면 이후의 `cd`를 해당 위치로 바꿉니다. 이후 명령은 별도 안내가 없으면 **GR-ER2/**에서 실행합니다.

<a id="gpu-driver"></a>
### 1.4 NVIDIA 드라이버 — 로봇 실습만

**실행 위치: 시뮬레이션 실습 호스트 · 설치 여부 확인**

```bash
nvidia-smi
df -h .
```

GPU와 드라이버가 표시되면 현재 버전을 확인합니다. Isaac Sim 6.0의 공식 Linux 테스트 버전은 **580.95.05**입니다. 장비에 맞는 호환 드라이버를 사용하고, 정상 동작 중인 GPU 서버의 드라이버는 임의로 교체하지 않습니다. [공식 버전 기준](https://docs.isaacsim.omniverse.nvidia.com/6.0.0/installation/requirements.html)

드라이버가 없는 **새 Ubuntu 워크스테이션**에서는 “소프트웨어 및 업데이트 → 추가 드라이버”를 열어 해당 GPU에 제공되는 호환 NVIDIA 드라이버를 선택하고 적용한 뒤 재부팅합니다. Secure Boot의 MOK 등록이 안내되면 재부팅 화면에서 완료합니다. 목록에 호환 버전이 없으면 [NVIDIA 드라이버 설치 안내](https://docs.nvidia.com/datacenter/tesla/driver-installation-guide/index.html)를 확인하고, 설치 후 `nvidia-smi`가 성공한 상태에서 진행합니다.

<a id="docker-setup"></a>
### 1.5 Docker Engine — 로봇 실습만

`docker version`에서 Client·Server가 정상 표시되면 설치 블록을 건너뜁니다. 아래는 **Docker가 없는 새 Ubuntu**용입니다. 기존 Docker Desktop·docker.io·containerd 구성은 자동으로 제거하지 않습니다. 충돌 패키지가 있으면 [공식 설치 안내](https://docs.docker.com/engine/install/ubuntu/)에 따라 기존 컨테이너를 보존하며 정리하세요.

**실행 위치: 시뮬레이션 실습 호스트 · Docker가 없는 경우 최초 1회**

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "$VERSION_CODENAME")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"
```

**로그아웃 후 다시 로그인**하세요. SSH는 종료 후 재접속합니다. docker 그룹은 관리자 수준 권한이므로 본인 실습 계정에만 추가합니다.

**실행 위치: 시뮬레이션 실습 호스트 · 재로그인한 새 터미널**

```bash
cd "$HOME/physical-ai-system-design/GR-ER2"
docker version
docker run --rm hello-world
```

`Hello from Docker!`를 확인합니다. `sudo docker`로만 실행하지 말고 일반 계정에서 통과해야 이후 스크립트가 작동합니다.

<a id="gpu-container"></a>
### 1.6 NVIDIA Container Toolkit — 로봇 실습만

Docker에 GPU를 전달하는 구성입니다. 이미 설치·구성됐다면 1.7의 GPU 검사부터 확인하세요. 아래 Docker 재시작은 다른 컨테이너에 영향을 줄 수 있으므로 작업을 마친 뒤 실행합니다. [NVIDIA 공식 설치 절차](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)

**실행 위치: 시뮬레이션 실습 호스트 · Toolkit이 없는 경우 최초 1회**

```bash
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | \
  sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -fsSL https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
  sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
  sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
sudo apt-get update
GR_TOOLKIT_VERSION=1.20.1-1
sudo apt-get install -y \
  nvidia-container-toolkit="$GR_TOOLKIT_VERSION" \
  nvidia-container-toolkit-base="$GR_TOOLKIT_VERSION" \
  libnvidia-container-tools="$GR_TOOLKIT_VERSION" \
  libnvidia-container1="$GR_TOOLKIT_VERSION"
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
```

위 Toolkit 버전은 문서 작성 시 공식 배포 기준입니다. 패키지가 없어 실패하면 저장소 설정과 공식 버전을 확인하세요. Isaac Sim·Python 패키지 버전은 임의로 올리지 않습니다.

### 1.8 Brev — 개인 PC 준비·계정·서버 생성

**워크스테이션 사양이 부족하면 이 절부터 진행합니다.** 개인 PC에는 GPU가 필요하지 않습니다. 설치·시뮬레이션은 Brev에서 하고, 개인 PC는 터미널과 브라우저만 사용합니다. 워크스테이션 경로의 1.1~1.7을 개인 PC에 실행하지 마세요.

#### 개인 PC 최초 준비

- Windows 11: 관리자 PowerShell에서 아래를 실행하고 재부팅합니다. Ubuntu 앱을 처음 열어 Linux 계정을 만든 뒤, 이후 Bash 명령은 이 Ubuntu 터미널에서 실행합니다.
- Ubuntu: 개인 PC 터미널을 사용합니다.
- macOS: 터미널을 사용합니다. `curl`·`tar`·`ssh`·`rsync`를 준비합니다.

**실행 위치: 개인 Windows PC · 관리자 PowerShell · WSL이 없을 때 최초 1회**

```powershell
wsl --install -d Ubuntu-24.04
```

**실행 위치: 개인 Ubuntu PC 또는 Windows의 WSL Ubuntu · SSH 미접속 · 최초 1회**

```bash
sudo apt-get update
sudo apt-get install -y curl ca-certificates tar openssh-client rsync
```

Brev CLI **0.6.335**를 강의용 폴더에 설치합니다. 같은 버전을 이미 사용 중이면 다운로드를 생략하고 `brev --version`으로 확인합니다.

**실행 위치: 개인 PC의 Bash 터미널 · SSH 미접속 · 최초 1회**

```bash
GR_BREV_DIR="$HOME/.local/share/gr-er2/brev-0.6.335"
mkdir -p "$GR_BREV_DIR"
case "$(uname -s)" in
  Linux) GR_PC_OS=linux ;;
  Darwin) GR_PC_OS=darwin ;;
  *) echo "Ubuntu/WSL 또는 macOS 터미널을 사용하세요"; exit 1 ;;
esac
case "$(uname -m)" in
  x86_64) GR_PC_ARCH=amd64 ;;
  arm64|aarch64) GR_PC_ARCH=arm64 ;;
  *) echo "지원하지 않는 PC 아키텍처"; exit 1 ;;
esac
GR_ARCHIVE="brev-cli_0.6.335_${GR_PC_OS}_${GR_PC_ARCH}.tar.gz"
curl -fL "https://github.com/brevdev/brev-cli/releases/download/v0.6.335/$GR_ARCHIVE" \
  -o "$GR_BREV_DIR/$GR_ARCHIVE"
tar -xzf "$GR_BREV_DIR/$GR_ARCHIVE" -C "$GR_BREV_DIR" brev
export PATH="$GR_BREV_DIR:$PATH"
brev --version
```

[계정·결제 설정은 Brev Console](https://brev.nvidia.com/)에서 합니다. NVIDIA 계정 로그인 → 사용할 조직 선택 → 결제 수단·비용 확인 순서로 준비합니다. Gemini API 결제와 별도입니다.

**실행 위치: 개인 PC · SSH 미접속 · 로그인·견적 확인**

```bash
export PATH="$HOME/.local/share/gr-er2/brev-0.6.335:$PATH"
brev login
brev ls
brev search gpu --gpu-name L40S --min-ram 64 --min-disk 250 --sort price --wide
brev create gr-er2-lab --type massedcompute_L40S --count 1 --mode vm --dry-run
```

Brev 구성은 **L40S 48GB 한 대, RAM 72GB, 디스크 625GB**입니다. 확인 당시 단가는 **$1.056/시간**이며 설치·다운로드·대기에도 과금됩니다. 현재 가격·재고는 위 견적을 기준으로 확인하세요. 이 type은 **중지·재시작을 지원하지 않으므로 실습 후 자료 회수 → 서버 삭제**가 필요합니다. 다른 type으로 바꾸면 OS·네트워크·드라이버를 다시 확인해야 합니다.

**실행 위치: 개인 PC · SSH 미접속 · 견적 확인 후 서버 최초 생성, 이때부터 과금**

```bash
brev create gr-er2-lab --type massedcompute_L40S --count 1 --mode vm --timeout 600
brev ls
brev refresh
mkdir -p "$HOME/.config/gr-er2"
printf '%s\n' 'gr-er2-lab' > "$HOME/.config/gr-er2/brev-instance"
brev shell gr-er2-lab
```

생성 도중 표시되는 `STARTING / BUILDING`에서는 기다립니다. `Ready`가 나온 뒤 접속합니다. 오래 걸린다고 생성 명령을 반복하면 서버가 추가될 수 있으므로 `brev ls`로 먼저 확인하세요.

## 2. Gemini Robotics ER 2 API 등록·확인

<a id="api-project"></a>
### 2.1 계정·프로젝트·결제·API 키 — 최초 1회

아래 작업은 **개인 PC의 웹 브라우저**에서 합니다.

1. [Google AI Studio](https://aistudio.google.com/)에 Google 계정으로 로그인하고 이용 조건을 확인합니다.
2. Dashboard의 **Projects**에서 실습용 프로젝트를 생성하거나 기존 Google Cloud 프로젝트를 가져옵니다. 키·결제·할당량은 같은 프로젝트를 선택합니다.
3. [Billing](https://aistudio.google.com/billing)에서 API 사용 가능 상태를 확인합니다. 선불 방식이면 크레딧을 충전하고 사용량·알림을 확인하세요. 유료 실험은 잔액과 요금을 확인한 뒤 시작합니다. 개인용 Gemini 구독과 API 결제는 별도입니다. [공식 API 결제 안내](https://ai.google.dev/gemini-api/docs/billing)
4. [API Keys](https://aistudio.google.com/apikey)에서 **Create API key**를 눌러 해당 프로젝트의 키를 생성합니다. 조직 계정에서 버튼이 막히면 프로젝트 관리자의 키 생성 권한이 필요합니다.
5. 새 키는 현재 AI Studio의 인증 키 정책을 따릅니다. 기존 표준 키가 `Unrestricted`이면 **Add restrictions → Restrict to Gemini API only**로 제한합니다. 서버 Python 호출용 키에 브라우저 도메인 제한을 지정하면 호출이 차단될 수 있습니다. [공식 키 발급·제한 안내](https://ai.google.dev/gemini-api/docs/api-key)

ER 2는 Gemini API의 모델 ID로 호출합니다. 로봇 모델 체크포인트 다운로드나 별도 ER 2 전용 키는 필요하지 않습니다. 프로젝트에서 모델 접근이 가능한지는 아래에서 확인합니다.

<a id="api-key"></a>
### 2.2 키 저장과 모델 확인

**실행 위치: 실습 호스트 · GR-ER2/ · 최초 키 등록**

<a id="agent-perturb"></a>
### 6.3 물체 위치를 바꿔보기

1. 수동 화면에서 **방해 주입: 빨간 블록 이동**을 누릅니다.
2. 위치가 바뀐 화면을 확인합니다.
3. ER 2에게 빨간 블록 정리를 다시 지시합니다.

동작 중에도 방해 버튼을 누를 수 있습니다. 방해는 빨간 블록을 정해진 위치로 강제 이동시키며 이벤트 기록에 남습니다. 진행 중인 저수준 동작은 처음 전달된 목표로 계속 진행할 수 있고, 다음 관찰에서 모델이 변경된 장면을 받습니다. 방해 직전 관측으로 새 행동을 요청하면 재촬영을 요구할 수 있습니다.

이 단계는 사례를 직접 살펴보는 실습입니다. 반복 횟수와 조건을 통제한 실패 복구 성능 평가는 별도 설계가 필요합니다.

<a id="recovery-experiment"></a>
### 6.4 자동 방해·재관찰·복구 비교

목표: 모델이 정한 첫 집기 위치에서 물체가 벗어난 뒤, 다음 관찰에서 새 위치를 선택해 작업을 마치는지 확인합니다.

1. 3절 또는 7절로 시뮬레이터와 웹 화면을 준비합니다.
2. 웹 화면의 **방해 후 재관찰·복구 실험 → 기준 조건 + 방해·복구 실행**을 누릅니다.
3. 장면 초기화와 최대 4회 모델 호출 안내를 확인하고 실행합니다. 실험 중 다른 방해·초기화 버튼을 누르지 않습니다.
4. 완료 후 결과의 `baseline`, `perturbed` 판정과 저장 영상을 확인합니다.

같은 실험을 실습 호스트 터미널에서 실행하려면 아래 명령을 사용합니다. 시뮬레이터는 먼저 켜져 있어야 합니다. 터미널 실행 중에는 웹 화면에서 다른 실험을 실행하지 않습니다.

**실행 위치: 실습 호스트 터미널 A · 폴더: GR-ER2/ · 선택: 비스트리밍 복구 비교 · API 비용 발생**

```bash
cd "$HOME/physical-ai-system-design/GR-ER2"
.venv/bin/python src/recovery.py
```

| 조건 | 수행 내용 |
|---|---|
| `baseline` | 장면 1 초기화 → ER 2 판단 1회 → 빨간 블록 집기·배치 |
| `perturbed` | 같은 장면 초기화 → 첫 행동 시작 60 tick(1초) 후 빨간 블록 이동 → 첫 행동 종료 → 새 이미지로 다음 판단. 최대 3회 판단 |

방해는 실험 코드가 정해진 시점에 물체를 다른 위치로 옮기는 조작입니다. 실제 외력이나 사람의 밀기를 모사한 조건은 아닙니다. 진행 중인 첫 행동은 원래 목표로 계속 수행하며, 다음 행동부터 모델의 새 판단을 사용합니다. 모델에는 방해의 정답 위치·성공 판정이 전달되지 않습니다.

결과는 `outputs/03_perturbation_recovery/<ID>/`에 저장합니다.

- `protocol.json`, `summary.json`: 실험 조건과 조건별 판정.
- 각 조건의 `step_XX/input.png`, `overlay.png`, `action.json`, `response.json`: 실제 모델 입력·좌표·응답.
- `perturbed/events/`: 방해 시각, 동작 tick과 위치 변화. 평가 전용 자료입니다.
- 각 조건의 `input_video/camera.mp4`, `rollout_video/side.mp4`: 모델 대기·방해·모든 행동을 포함한 전체 관찰 영상.
- 각 조건의 `actions/step_XX/`: 행동별 영상·최종 이미지·평가값.
- `recording.json`: 영상 FPS·시간축. 영상은 10 FPS, 시뮬레이션 시간 기준이며 모델 입력은 단계별 이미지입니다.

`recovery_observed: true`는 **방해 기록 + 첫 행동 배치 실패 + 이후 빨간 블록 배치 성공 + 마지막 트레이 내부 위치**가 함께 확인됐다는 뜻입니다. `controller_status: completed`만으로 복구 성공을 판정하지 않습니다. API 오류는 `error.json`에 남으며, 부분 실행 결과를 복구 성공으로 해석하지 않습니다. 조건당 한 번의 사례 확인이므로 일반적인 복구 성공률을 뜻하지 않습니다.

실습이 끝나면 9절에 따라 서버를 종료합니다.

<a id="live-recovery-experiment"></a>
### 6.5 Live 카메라 스트리밍으로 동작 중 감지·복구

목표: 첫 행동이 진행되는 동안 모델이 카메라에서 물체 이동을 감지해 행동을 중단하고, 새 위치로 복구하는지 확인합니다.

[공식 Robotics Streaming 안내](https://ai.google.dev/gemini-api/docs/robotics-streaming)에 따라 `gemini-robotics-er-2-streaming-preview`와 Live API WebSocket을 사용합니다. JPEG 프레임 입력은 최대 1 FPS이며, 프레임만 보내면 판단이 자동 시작되지 않아 짧은 heartbeat 지시를 함께 사용합니다. 앞선 판단 턴이 끝난 뒤 다음 지시를 보내고, 실제 물리 행동 도구는 `BLOCKING`으로 선언합니다.

실험 구성:

1. 일반 ER 2가 초기 이미지로 첫 집기 행동을 계획합니다.
2. 별도의 Live 감독 세션에 고정 카메라 프레임을 지속 전송합니다. 첫 행동이 실행되는 동안에도 전송을 유지합니다.
3. 실험 코드가 첫 행동 시작 60 tick 후 빨간 블록을 이동시킵니다. 이동 시점·정답 좌표는 모델에 전달하지 않습니다.
4. Live 모델이 `target_moved`를 보고하면 실행기가 현재 관절 목표를 유지하고 진행 중인 행동을 종료합니다.
5. 로봇을 관찰 자세로 복귀시킵니다. 물체의 위치는 초기화하지 않습니다. 같은 Live 세션이 새 영상에서 `recover_pick_place`를 호출하고, 동작 이후 성공 여부를 다시 관찰합니다.

**초기 행동은 일반 ER 2, 동작 중 감독과 복구는 ER 2 Streaming이 담당하는 혼합 구성**입니다. 모델의 관찰 주기·API 지연과 60 Hz 관절 제어 주기는 서로 다릅니다. 이 실험의 중단 기능은 시뮬레이션 전용이며 실제 로봇의 안전 정지 장치로 사용하지 않습니다.

실행 순서:

1. 3절 또는 7절로 시뮬레이터와 웹 화면을 켭니다.
2. **Live 스트리밍 · 동작 중 감지·중단·복구 → Live 스트리밍 방해·복구 실행**을 누릅니다.
3. 실행 중 추가 방해·다른 실험 버튼은 누르지 않습니다. 최초 API 계획 후 Live 세션을 최대 240초·24개 판단 턴으로 제한합니다. 모델 응답과 종료·영상 인코딩 때문에 전체 경과 시간은 더 길 수 있습니다.
4. 결과의 `interrupted_while_action_active`와 `streaming_recovery_observed`를 함께 확인합니다. 행동이 끝난 뒤 감지했다면 동작 중 중단 성공으로 기록하지 않습니다.

터미널에서 같은 실험을 실행하려면 실습 호스트에서 다음 명령을 사용합니다. 시뮬레이터가 준비되어 있어야 하며 웹 화면에서 중복 실행하지 않습니다.

**실행 위치: 실습 호스트 터미널 A · 폴더: GR-ER2/ · 기본 target_shift 실행 · 6.6 S1과 중복 실행하지 않음**

```bash
cd "$HOME/physical-ai-system-design/GR-ER2"
.venv/bin/python src/live_recovery.py
```

**실행 위치: 실습 호스트 터미널 A · 폴더: GR-ER2/ · 본 실험 전 Live 연결 검사**


### 6.6 세 가지 교란과 입력·판단 통합 영상

시뮬레이터를 시작한 뒤 웹 화면의 **Live 스트리밍 → 시나리오**에서 한 가지를 선택해 실행합니다. 각 실행은 초기 장면부터 시작하며 유료 API를 호출합니다. 다음 명령으로도 하나씩 실행할 수 있습니다. 웹 버튼과 터미널 명령을 동시에 실행하지 않습니다.

**실행 위치: 실습 호스트 터미널 A · 폴더: GR-ER2/ · 각 시나리오 순차 실행 · 이미 실행한 S1은 생략 · API 비용 발생**

```bash
# S1: 집기 대상 이동 → 새 위치를 보고 재파지
.venv/bin/python src/live_recovery.py --scenario target_shift

# S2: 목적지 트레이 이동 → 현재 트레이 위치로 재계획
.venv/bin/python src/live_recovery.py --scenario goal_shift

# S3: 운반 중 낙하 → 떨어진 물체를 다시 집기
.venv/bin/python src/live_recovery.py --scenario grasp_drop
```

| 실험 | 주입 방법 | 확인할 판단 |
|---|---|---|
| S1 대상 이동 | 첫 동작 60 tick에 빨간 블록 위치 변경 | 원래 집기 위치가 더 이상 유효한지 |
| S2 목적지 이동 | 첫 동작 60 tick에 빈 트레이 전체를 X 방향 -18 cm 이동 | 이전 배치 좌표와 현재 목적지의 차이 |
| S3 파지 해제·낙하 | 블록이 12 cm 이상 들리면 첫 동작 동안 그리퍼를 열어 유지 | 운반 도중 물체를 잃었는지, 다시 집을 위치 |

S1·S2의 위치 변경은 명시적인 실험 교란입니다. S3은 실제 접촉으로 들어 올린 블록을 그리퍼 개방으로 놓으며, 낙하 위치는 물리 계산으로 결정됩니다. 주입 기록·정답 물체 좌표는 평가에만 사용합니다. 모델은 RGB 스트림과 작업 지시로 상황을 판단합니다. 복구 도구가 실행되는 동안에도 프레임은 전송되며, 다음 판단은 도구 응답 이후 시작됩니다.

연구의 문제 설정을 참고한 **교육용 세 가지 사례**입니다. [QT-Opt](https://research.google/blog/scalable-deep-reinforcement-learning-for-robotic-manipulation/)의 이동 대상 대응·파지 중 물체 손실과 재파지, [Inner Monologue](https://innermonologue.github.io/)의 실패 피드백·목표 변화 후 재계획을 참고했습니다. S2의 트레이 이동은 목표 변화라는 문제를 현재 장면에 적용한 구성입니다. 원 논문의 알고리즘·환경·성공률을 재현한 벤치마크로 해석하지 않습니다.

영상에서 변화 감지·동작 중단·최종 배치를 각각 확인합니다. 각 시나리오는 개별 사례이며, 반복 성공률이나 모델 간 성능 비교는 측정하지 않았습니다. 모든 실험을 마치면 **9절 종료**를 진행합니다.

각 실행 시작 전에 로봇과 서랍을 초기화합니다. 실행 중에는 **손가락 열기 → 안전 높이 이동 → 손잡이 앞 정렬 → 접근 → 양쪽 손가락 접촉 확인 → 저속 당기기 → 놓기 → 후퇴 → 안정화**를 수행합니다. 당기는 동안 서랍 위치를 직접 변경하거나 로봇에 붙이는 고정 제약을 만들지 않습니다. 실제 접촉으로 움직입니다. 재시도 때 팔을 초기 관절 자세로 강제 복귀하지 않습니다. 물리·제어는 120 Hz, 렌더링 60 FPS, 원본 녹화 10 FPS입니다.

위 서랍은 수동 서랍(`stiffness=0`, `damping=10`)으로 구성합니다. 두 번째 서랍과 다른 문은 원래 관절 설정을 유지하며 강제로 잠그지 않습니다. 팔·그리퍼의 제어 gain은 동작 중 일정하게 유지합니다. 관절 목표 변화량은 최대 0.5 rad/s, 관절 속도 설정은 0.7 rad/s이며 실제 과속(1 rad/s 초과) 또는 두 번째 서랍의 1 cm 초과 이동은 동작 중단 사유입니다. 사용한 제어·환경 설정은 `policy_sources.json`에 저장합니다.

**성공 기준:** 위 서랍 15 cm 이상 개방, 두 번째 서랍 이동 1 cm 이하, 다른 문 회전 0.02 rad 이하, 팔 속도 1 rad/s 이하, 양쪽 손가락의 손잡이 접촉 확인, 놓기·후퇴 완료, 마지막 1.5초 안정화가 함께 필요합니다. `--smoke`의 `task_success`는 `null`이며 `motion_quality_passed`와 `manual_result.json`을 봅니다. 동작 실패 시 API 실험에 앞서 원본 영상과 `controller_phase`를 확인합니다. 품질 계측이 없는 과거 자료는 새로운 성공 기준을 통과하지 않습니다.

복구 실험에서는 닫힘 주입 직전에 서랍이 15 cm 이상 열려 있고 그리퍼가 손잡이에서 7 cm 이상 물러나 있는지도 확인합니다. 이후 재열기 호출 직전 실제로 닫혀 있었는지, 호출 후 다시 열렸는지를 검사합니다.

GUI에서 실행하려면 3.2·3.3절로 웹 화면을 열고 **다른 환경 → Franka 서랍 닫힘·재열기**를 누릅니다. 같은 실험의 터미널 명령과 웹 버튼을 동시에 실행하지 않습니다. 전체 Isaac Sim 창이 필요하면 7절의 방식으로 다음 중 하나를 사용합니다.

**실행 위치: 호스트 모니터의 데스크톱 터미널 · 폴더: GR-ER2/ · 선택 A: 직접 GUI, 아래 B와 택일**

```bash
GR_ER2_SCENE=drawer bash scripts/sim.sh gui
```

```bash

GR_ER2_SCENE=drawer bash scripts/sim.sh stream "$SERVER_IP"
```

화면 모드를 전환하기 전에는 `bash scripts/sim.sh stop`으로 기존 프로세스를 종료합니다.

결과는 `outputs/05_drawer/<ID>/`입니다. `input_video/camera.mp4`는 모델 관찰 카메라 전체 기록, `rollout_video/side.mp4`는 다른 각도의 실제 동작, `presentation/synchronized.mp4`는 입력·요청·응답 통합 영상입니다. `--smoke`는 API 입력이 없어 원본 영상과 물리 평가만 저장합니다.

**해석:** 저수준 도구는 시뮬레이터에서 읽은 정확한 손잡이 pose·관절 상태·접촉력을 사용합니다. `lift/align` 등의 전환은 위치 오차·속도·시간·접촉 조건을 검사하는 직접 작성한 상태 머신입니다. ER 2에는 RGB와 도구 종료 상태를 전달하며, 도구 선택·시각 상태 판단을 맡깁니다. 서랍의 하위 제어에 별도 카메라 인식기는 없습니다. 닫힘은 외부 개입을 단순화한 서랍 관절 위치 변경입니다. 역할과 실물 이전 시 필요한 부분은 [폐루프 설명](./docs/폐루프_구성과_모델_제어기_역할.md)에 정리했습니다.

### 6.8 새 환경 — Spot 실내 점검

작은 실내 공간에서 Spot이 설비 앞까지 걸어가 표시등 색을 확인합니다. 짧은 중앙 통로와 오른쪽 우회 통로를 제공하며, 교란 조건에서는 이동 중 중앙 통로에 장애물을 삽입합니다. 빠른 장애물 정지는 로컬 레이캐스트 검사로 처리하고, ER 2가 새 영상과 도구 결과를 바탕으로 다음 경로를 선택합니다.

**실행 위치: 워크스테이션 터미널 A · GR-ER2/ · Brev는 7.5 장면 전환 후 아래 실험부터 실행**

```bash
bash scripts/sim.sh stop
GR_ER2_SCENE=patrol bash scripts/sim.sh start
bash scripts/sim.sh logs
```

`GR_ER2_READY patrol`을 확인하고 `Ctrl+C`로 로그 보기를 끝냅니다. 처음에는 공식 Spot USD와 `Spot_Policies/spot_policy.pt`, `spot_env.yaml`을 읽습니다.

**실행 위치: 실습 호스트 터미널 A · 폴더: GR-ER2/**

```bash
# 본 실험: 실제 Live API 경로 선택 + 차단 후 우회 + 표시등 판단
.venv/bin/python src/scenario_run.py patrol
```

선택 점검과 교란 없는 조건은 별도 실행입니다. smoke에서 `blocked`는 중앙 경로의 로컬 장애물 정지를 확인하는 값입니다. API가 없으므로 우회·표시등 판단까지 수행하지 않습니다.

**실행 위치: 실습 호스트 터미널 A · 폴더: GR-ER2/ · 선택 실험 · 필요한 조건만 실행**

```bash
# 선택: API 없이 중앙 경로의 보행과 장애물 정지 검사
.venv/bin/python src/scenario_run.py patrol --smoke
# 선택: 교란 없는 기준 조건
.venv/bin/python src/scenario_run.py patrol --no-perturb
```

웹 화면에서는 **다른 환경 → Spot 통로 차단·우회·설비 점검**을 사용합니다. 호스트 모니터와 원격 WebRTC는 6.7절 명령의 `GR_ER2_SCENE=drawer`를 `GR_ER2_SCENE=patrol`로 바꿉니다. 블록 전용 조작 버튼은 사용하지 않습니다.

결과는 `outputs/06_patrol/<ID>/`이며 폴더 구성은 서랍 실험과 같습니다. 여기서 입력 카메라는 로봇 위치·진행 방향을 따라가는 전방 RGB 카메라이고, 동작 영상은 환경 전체를 보는 고정 카메라입니다.

**해석:** 이동은 공식 Spot 평지 보행 정책, 시뮬레이터 기반 자기 위치, 사전에 정의한 경유점 경로를 사용합니다. ER 2가 선택하는 것은 `center` 또는 `right` 경로와 완료·표시등 판단입니다. 새 지도를 만드는 SLAM이나 자유 공간 전체에 대한 경로 탐색은 포함하지 않습니다. 목표 도착·전도 여부·표시등 판독을 각각 기록합니다.

Spot의 물리는 공식 checkpoint 설정의 500 Hz, 정책 추론은 10 tick마다 한 번인 50 Hz입니다. 렌더링과 원본 영상 저장은 각각 50 FPS·10 FPS입니다. 실제 장비 성능에 따라 벽시계 기준 재생 속도는 달라지므로 통합 영상은 별도 타임스탬프로 정렬합니다.

두 실험 모두 Live 세션 최대 360초·18개 턴·물리 도구 최대 4회로 제한합니다. 종료·영상 인코딩 시간은 별도입니다. API 원문은 `turn_XX/`, 실제 전송 JPEG는 `sent_frames/`, 물리 평가는 `evaluation_trace.jsonl`과 `evaluation.json`, 제어 설정은 `policy_sources.json`에 저장합니다. **검증 결과는 [새 환경 결과 안내](./docs/새환경_실험결과.md)**를 참고합니다. 완료 후 9절에 따라 시뮬레이터·웹 서버를 종료하세요.

주요 장면 사진은 각 실행의 `materials/`에 자동 저장합니다. 원본 프레임 번호·실제 시각·이벤트 표를 함께 보관합니다. 저장 데이터만으로 자료를 다시 만드는 명령은 다음과 같습니다(추가 API 호출·시뮬레이터 실행 없음).

**실행 위치: 실습 호스트 터미널 A · 폴더: GR-ER2/ · 결과 생성 후 · <실행_ID>를 실제 값으로 변경**

```bash
.venv/bin/python src/scenario_materials.py 'outputs/05_drawer/<실행_ID>'
.venv/bin/python src/validate_recording.py 'outputs/05_drawer/<실행_ID>'
# Spot은 경로를 outputs/06_patrol/<실행_ID>로 변경
```

서랍의 이전 개방량 중심 성공 판정은 동작 품질 재검토 후 철회했습니다. 최신 실측과 Spot 결과는 위 결과 안내에서 확인합니다. 개별 실행 사례이며 모든 재실행의 성공을 보장하지 않습니다.

<a id="dual-franka"></a>
### 6.9 두 Franka — 협업 키트 준비·전달 실패 복구

**목적:** 두 팔이 서로 다른 색의 블록을 전달해 각자의 녹색 트레이에 빨강·파랑 한 개씩을 넣습니다. ER 2가 로봇, 좌표, 작업 순서와 재시도를 선택합니다. 중앙 노란 전달 구역에는 한 번에 한 팔만 들어갈 수 있습니다. 독립 작업은 비동기 `job_id`로 동시에 진행합니다.

1·2절의 설치와 API 키가 필요합니다. 아래 명령은 **실습 호스트의 프로젝트 폴더**에서 실행합니다. 현재 실행 중인 다른 실험을 먼저 마칩니다.

**실행 위치: 워크스테이션 터미널 A · GR-ER2/ · Brev는 7.5에서 dual_franka로 전환 후 아래 제어 점검부터 실행**

```bash
cd "$HOME/physical-ai-system-design/GR-ER2"
bash scripts/sim.sh stop
GR_ER2_SCENE=dual_franka bash scripts/sim.sh start
bash scripts/sim.sh logs
```

로그의 `GR_ER2_READY dual_franka`를 확인합니다. `logs`에서 `Ctrl+C`는 로그 보기만 종료합니다. 물리 시뮬레이터는 계속 실행됩니다.

**실행 위치: 실습 호스트 터미널 A · 폴더: GR-ER2/ · 선택 심화 · 제어 검사 후 정상/예외 조건 순차 실행**

```bash
# 최초 제어 점검: 사전에 정한 좌표로 두 팔을 움직임. API 호출 없음, ER 2 결과와 별도 보관
.venv/bin/python src/coop_smoke.py --scene dual_franka

# 정상 조건: 각 트레이에 두 색을 배치
.venv/bin/python src/coop_run.py --scene dual_franka --condition normal

# 첫 중앙 전달 시도에서 그리퍼가 열려 있게 함. ER 2에는 발생 시점·정답을 제공하지 않음
.venv/bin/python src/coop_run.py --scene dual_franka --condition exception
```

한 실행이 끝난 뒤 다음 명령을 실행합니다. 각 실행의 첫 출력은 결과 폴더입니다. `outputs/07_cooperative/dual_franka/<normal 또는 exception>/<ID>/`에 저장합니다. 실험마다 API 비용이 발생하고, 기본 제한은 55개 판단 턴·1,500초입니다. API 요청과 종료 처리 때문에 최종 반환까지 추가 시간이 걸릴 수 있습니다. 제한 안에 완료되지 않은 결과도 그대로 저장합니다.

중간에 멈추려면 실험 터미널에서 `Ctrl+C`를 누른 뒤 `bash scripts/sim.sh stop`으로 시뮬레이터를 종료합니다. 같은 설정에서도 API 응답과 물리 결과는 달라질 수 있습니다.

직접 3D 화면을 보려면 위 `start` 대신 호스트 모니터에서는 `GR_ER2_SCENE=dual_franka bash scripts/sim.sh gui`, 원격에서는 7.2절의 `stream` 명령에 `GR_ER2_SCENE=dual_franka`를 붙입니다. **협업 실험의 실행은 CLI를 사용합니다. 기존 웹 페이지의 단일 로봇 조작 버튼은 사용하지 않습니다.** GUI의 관절·물체를 수동으로 바꾸면 기록된 실험 조건이 달라집니다.

**역할 구분:** ER 2는 RGB와 공개 작업 응답으로 판단합니다. 2D 선택을 실제 조작으로 연결할 때는 알려진 5 cm 블록 크기, RGB-D 역투영, RMPFlow 기반 공식 PickPlaceController, 로봇 관절 상태를 사용합니다. 하위 제어의 종료는 `sequence_completed`로 반환하며, 물체 전달 성공을 의미하지 않습니다. 모델이 다시 확인해야 합니다. 실제 물체 위치는 평가용 `truth.jsonl`에 별도 저장합니다.

### 6.10 Franka–Spot–Franka — 자재 운송과 실패 복구

**목적:** 컨베이어 A의 빨간 자재를 Franka A가 Spot 적재함에 싣고, Spot이 약 4m 떨어진 B로 운반하면 Franka B가 컨베이어 B로 내립니다. ER 2가 로봇·도구 순서, 적재 확인, 재시도, 우회와 완료 판단을 담당합니다.

프로젝트 폴더에서 실행합니다. 앞 실험과 동시에 실행하지 않습니다.

**실행 위치: 워크스테이션 터미널 A · GR-ER2/ · Brev는 7.5에서 transport로 전환 후 아래 제어 점검부터 실행**

```bash
bash scripts/sim.sh stop
GR_ER2_SCENE=transport bash scripts/sim.sh start
bash scripts/sim.sh logs
```

`GR_ER2_READY transport` 확인 후 로그 보기를 종료합니다. 직접 모니터에서는 `start`를 `gui`로 바꿉니다. 원격 화면은 7.2절의 `stream` 명령에 `GR_ER2_SCENE=transport`를 붙입니다.

**실행 위치: 실습 호스트 터미널 A · 폴더: GR-ER2/ · 선택 심화 · 제어 검사 후 각 조건 순차 실행**

```bash
# 제어 점검: 정확한 시뮬레이터 좌표로 인계·운반·하역. API 호출 없음
.venv/bin/python src/transport_smoke.py --condition normal

# 아래 실험부터 실제 ER 2 API 사용. 하나가 끝난 뒤 다음 명령 실행
.venv/bin/python src/coop_run.py --scene transport --condition normal
.venv/bin/python src/coop_run.py --scene transport --condition load_failure
.venv/bin/python src/coop_run.py --scene transport --condition obstacle
```

- `normal`: 적재 → 실제 운반 → 하역.
- `load_failure`: 첫 적재 시 그리퍼를 열어 파지를 실패시킵니다. ER 2가 관찰 후 출발 보류·재시도를 선택하는지 봅니다.
- `obstacle`: 운반 중 직선 통로에 실제 장애물을 배치합니다. 안전 제어가 정지한 후 ER 2가 관찰하고 우회 경로를 선택하는지 봅니다.

결과는 `outputs/07_cooperative/transport/<조건>/<실행_ID>/`에 저장합니다. 모델은 작업장 A/B·Spot 전방·적재함 카메라의 이미지와 직전 최대 6초 영상을 받습니다. 전체 카메라는 시청자와 별도 사후 평가용으로 저장하며 운송 판단 API에는 제공하지 않습니다. 집기 지점은 모델이 지정한 점 주변의 국소 깊이 영상으로 윗면 중심을 보정합니다. 이 과정과 원래 좌표는 `events.jsonl`에 기록합니다. 물체의 시뮬레이터 정답 위치로 보정하지 않습니다.

**구현 범위:** 컨베이어는 인계 위치에서 정지한 작업대입니다. 이 실험의 완료 조건은 B 컨베이어에 내려놓는 것입니다. 5cm 자재는 동적 강체이며, 초기화 후 순간 이동하거나 Spot에 고정하지 않습니다. 적재함은 Spot 몸체에 붙인 충돌 형상입니다. 하위 제어는 RGB-D 좌표 변환·공식 Franka 제어기·공식 Spot 보행 정책·시뮬레이터 자기 위치·알려진 경유점·안전 정지를 사용합니다. API에 숨겨진 물체 위치는 사후 평가에 사용합니다. Spot 이동 중 팔 작업과 팔 인계 중 이동은 인터록으로 제한합니다. 재시도·우회 판단은 모델이 합니다.

기본 한도는 55턴·1,500초입니다. 시간 제한 도달과 실패도 기록합니다. 결과 정리는 다음 6.11절을 따릅니다.

### 6.11 협업 실험의 영상·진행률·결과 정리

**실행 위치: 실습 호스트 터미널 A · 폴더: GR-ER2/ · 결과 생성 후 · API 평가 2회 포함, 마지막 줄은 실습 종료 시에만**

```bash
.venv/bin/python src/coop_validate.py 'outputs/07_cooperative/dual_franka/normal/<실행_ID>'
```

| 자료 | 파일·폴더 | 읽는 방법 |
|---|---|---|
| 가장 먼저 볼 영상 | `presentation/synchronized.mp4` | 물리 장면·실제 API 입력·응답·독립적인 로봇 작업 상태 |
| 전체 원본 카메라 영상 | `input_video/overview.mp4`, `A.mp4`, `B.mp4` (운송은 `Spot.mp4`, `cargo.mp4` 추가) | 계속 녹화된 원본. 전체가 API에 입력된 것은 아님 |
| 관측 원본과 제출 기록 | `api_inputs/`, `api/*/request.json` | 두 Franka 키트 실험은 이미지, 자재 운송은 이미지·확보된 과거 영상을 제출. 요청별 관측 ID·시각 확인 |
| 실제 로봇 동작 영상 | `rollout_video/side.mp4` | 고정 제3자 카메라의 실제 시뮬레이션 결과 |
| 모델 원문·도구 호출 | `api/`, `model_timeline.json`, `model_report.json` | 모델 선택·공개 도구 응답·완료 주장 |
| 물리 평가·동시 실행 | `summary.json`, `jobs.csv`, `truth.jsonl` | 모델에 숨겨 둔 실제 상태와 대조 |
| 실제 좌표 보정 입력 | `control_inputs/` | 집기에 사용한 원본 깊이·RGB·카메라 정보. API 입력과 구분 |
| 주요 장면 사진 | `figures/` | 초기·교란·최종·통합 화면 |
| 자재 인계 4장 비교 | `figures/handoff_storyboard.jpg` | A 입력·적재·B 도착·하역. 미도달 단계는 표시 |
| 영상 진행률 평가 | `video_progress/` | 실제 입력 prefix 영상·모델 원문·정답 비교 |
| 자료 자동 검증 | `validation.json` | 영상 디코딩·기록 수·시각·물리 점수 재계산 |

원본 영상은 5 FPS·시뮬레이션 시간 기준이고, 통합 영상은 동일 시간축에서 2.5 FPS로 구성합니다. API 입출력은 실제 벽시계 타임스탬프에 맞춰 표시합니다. 응답이 바뀌지 않는 동안에도 하위 제어가 진행될 수 있습니다. 화면에 다 담지 못한 원문은 `api/`에서 확인합니다.

자재 운송의 영상 완료 시각은 자재의 배치·그리퍼 해제·안정화를 기준으로 합니다. 팔이 초기 자세로 돌아온 시각은 별도 필드로 제공합니다. `api_inputs/`에는 요청 사이에 다시 촬영해 교체된 관측도 포함되므로 실제 API 제출 목록은 `submitted_inputs.json` 및 요청별 `request.json`을 기준으로 확인합니다.

영상 평가는 [공식 진행률/완료 시점 인터페이스](https://ai.google.dev/gemini-api/docs/robotics-video-progress)를 참고했습니다. Franka 진행률은 트레이별 색 배치 4개 요구사항, 자재 운송 진행률은 적재·자재를 싣고 출발·자재와 함께 도착·하역의 4개 이력 조건입니다. 자재 운송의 별도 영상 평가는 전체 화면을 사용하므로 현장 판단과 입력 조건이 다릅니다. 재생 영상에서 모델이 완료했다고 해도 실제 평가값과 함께 확인해야 합니다. 조건별 개별 사례로, 반복 성공률이나 모델 간 성능 비교는 측정하지 않았습니다.

자료 생성 시 `outputs/07_cooperative/results.csv`와 결과 목차 `README.md`도 갱신합니다. 조건별 결과는 [협업 실험 결과](./docs/협업_실험결과.md)를 참고하세요.

`video_progress/*/response.json`의 상태가 `incomplete`이면 출력 한도로 응답이 잘린 경우를 확인합니다. 아래 명령은 기존 불완전 원문을 `previous_incomplete_*`로 보존하고 해당 영상만 다시 호출합니다. 완료된 다른 응답은 다시 호출하지 않습니다. 재평가만 필요하면 `--reuse`를 사용합니다.

**실행 위치: 실습 호스트 터미널 A · 폴더: GR-ER2/ · 선택: 불완전 응답만 재요청 / 저장 응답 재평가 · 실제 실행 ID로 변경**

```bash
.venv/bin/python src/coop_progress.py 'outputs/07_cooperative/transport/normal/<실행_ID>' --retry-incomplete
.venv/bin/python src/coop_progress.py 'outputs/07_cooperative/transport/normal/<실행_ID>' --reuse
```

원본 프레임과 모델 입력 영상까지 포함해 회수하려면 8.3절의 복사 대상에 `outputs/07_cooperative/`를 포함합니다. 서버 종료만으로 결과 파일이 지워지지는 않습니다.

## 7. 선택 — Isaac Sim 전체 3D 화면

<a id="gui-choice"></a>
### 7.1 화면 모드 선택

| 보고 싶은 화면 | 시작 방법 | 조작 |
|---|---|---|
| 웹 카메라·실습 버튼 | 3.1 `start` | 브라우저 |

<a id="gui-remote"></a>
### 7.2 원격 WebRTC — 선택

3.3의 웹 카메라만으로 기본 실습을 할 수 있습니다. 전체 3D 창이 필요할 때만 아래를 진행합니다.

1. 개인 PC에서 [공식 WebRTC Streaming Client](https://docs.isaacsim.omniverse.nvidia.com/6.0.0/installation/manual_livestream_clients.html)의 OS별 설치 파일을 받습니다. 이 프로젝트에서 확인한 클라이언트는 **2.0.0**입니다. Linux는 다운로드한 deb를 설치하고 Windows/macOS는 해당 설치 프로그램을 사용합니다.
2. 개인 PC에서 실습 호스트로 **TCP 49100 / UDP 47998**이 직접 도달하는 LAN/VPN 경로를 준비합니다. SSH `-L`만으로 UDP 영상은 전달되지 않습니다. 임의의 클라우드 포트 매핑이 이 경로와 같다고 가정하지 마세요.
3. 호스트의 LAN/VPN IPv4를 사용합니다. 접속용 공인 IP와 내부 IP가 다른 서버는 먼저 네트워크 관리자와 접근 경로를 확인하세요. 포트를 인터넷 전체에 개방하지 않습니다.

**실행 위치: 개인 Ubuntu PC · WebRTC deb 다운로드 후 최초 1회**

```bash
read -r -p "다운로드한 WebRTC Client .deb의 전체 경로: " GR_CLIENT_DEB
sudo apt-get install "$GR_CLIENT_DEB"
```

**실행 위치: 실습 호스트 터미널 A · GR-ER2/ · 기존 실험 종료 후**

```bash
bash scripts/sim.sh stop
read -r -p "개인 PC에서 접근 가능한 이 GPU 호스트의 IPv4: " SERVER_IP
bash scripts/sim.sh stream "$SERVER_IP"
bash scripts/sim.sh logs
```

`GR_ER2_READY` 확인 후 Ctrl+C로 로그를 끝냅니다. 개인 PC 앱 메뉴에서 **Isaac Sim WebRTC Streaming Client**를 열고 아래를 입력합니다.

| 클라이언트 항목 | 값 |
|---|---|
| Server | 위에서 입력한 호스트 IPv4 |
| Signal | 49100 |
| Stream | 47998 |
| Resolution | 1280 × 720 |

5·6.1~6.8은 3.2·3.3의 웹 화면으로 지시하고, 협업은 6.9·6.10의 CLI로 실행합니다. WebRTC 연결에 실패해도 3.1·3.3의 웹 카메라 경로를 사용할 수 있습니다.

<a id="gui-local"></a>
### 7.3 직접 연결된 모니터 — 선택

호스트의 Ubuntu 데스크톱에 로그인해 터미널을 엽니다. 이 스크립트는 **X11/Xorg 세션**을 사용합니다. Wayland면 로그아웃 후 로그인 화면의 세션 선택에서 “Ubuntu on Xorg”를 선택합니다.

**실행 위치: GPU 호스트에 연결된 모니터의 데스크톱 터미널 · SSH 접속 터미널에서 실행하지 않음**

```bash
cd "$HOME/physical-ai-system-design/GR-ER2"
echo "$XDG_SESSION_TYPE"
echo "$DISPLAY"
bash scripts/sim.sh stop
GR_ER2_SCENE=blocks bash scripts/sim.sh gui
bash scripts/sim.sh logs
```

`GR_ER2_READY` 확인 후 Ctrl+C로 로그 보기만 끝냅니다. 창에 Franka·블록·트레이가 표시됩니다. 스크립트가 현재 디스플레이의 인증 쿠키를 복사합니다. `xhost +`로 접근 제어를 해제하지 않습니다. 별도 터미널 B에서 3.2 웹 서버를 실행하고 같은 컴퓨터의 브라우저를 엽니다. 시뮬레이션은 자동 시작하므로 Play를 따로 누를 필요는 없습니다.

<a id="gui-stop"></a>
### 7.4 모드 전환과 종료

Stage·관절 값을 임의로 바꾸면 실험 조건도 바뀝니다. 종료는 9절입니다. 창을 닫아도 웹 서버나 다른 프로세스가 남을 수 있으므로 컨테이너 종료까지 확인합니다. 카메라 전용·원격 모드는 `gr-er2-sim`, 직접 GUI는 `gr-er2-sim-gui`를 사용합니다.

<a id="brev-gui"></a>
### 7.5 Brev — 브라우저에서 전체 GUI 실행

1.8~1.9 설치와 2절 키 등록을 마친 뒤 진행합니다. **5절 수동 제어만 확인할 때는 API 키 없이 실행할 수 있습니다.** 이 경로는 SSH 터널과 브라우저를 사용하며, 화면은 서버에서 실행되는 실제 Isaac Sim 데스크톱 GUI입니다. WebRTC 앱·공인 IP 입력·UDP 포트 개방은 필요하지 않습니다.

#### 매번 시작 — 터미널 A

**실행 위치: 개인 PC · 새 터미널 A · SSH 미접속**

```bash
export PATH="$HOME/.local/share/gr-er2/brev-0.6.335:$PATH"
export BREV_INSTANCE="$(cat "$HOME/.config/gr-er2/brev-instance")"
brev ls
brev refresh
brev shell "$BREV_INSTANCE"
```

이 문서에서 사용하는 type은 중지를 지원하지 않습니다. 삭제한 서버라면 1.8에서 새로 생성·설치합니다. 다른 중지 가능한 type을 선택했다면 Console에서 시작한 뒤 접속합니다.

**실행 위치: 방금 접속한 Brev 서버 터미널 A · 매번 실행**

```bash
cd "$HOME/physical-ai-system-design/GR-ER2"
GR_ER2_SCENE=blocks bash scripts/cloud_gui.sh start
bash scripts/sim.sh logs
```

`GR_ER2_READY`를 확인한 뒤 **Ctrl+C로 로그 보기만 종료**합니다. 첫 실행은 셰이더·asset 준비로 오래 걸릴 수 있습니다. 창이 떴더라도 장면 준비 로그 전에는 실험을 시작하지 않습니다.

#### 웹 실습 서버 — 터미널 B

**실행 위치: 개인 PC · 새 터미널 B · SSH 미접속**

```bash
export PATH="$HOME/.local/share/gr-er2/brev-0.6.335:$PATH"
export BREV_INSTANCE="$(cat "$HOME/.config/gr-er2/brev-instance")"
brev shell "$BREV_INSTANCE"
```

**실행 위치: 방금 접속한 Brev 서버 터미널 B · 실행한 채 유지**

```bash
cd "$HOME/physical-ai-system-design/GR-ER2"
bash scripts/web.sh
```

#### 화면 연결 — 터미널 C

**실행 위치: 개인 PC · 새 터미널 C · SSH 미접속 · 실행한 채 유지**

```bash
export BREV_INSTANCE="$(cat "$HOME/.config/gr-er2/brev-instance")"
ssh -NT -o ControlMaster=no -o ControlPath=none -o ControlPersist=no \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:6080:127.0.0.1:6080 \
  -L 127.0.0.1:8765:127.0.0.1:8765 "$BREV_INSTANCE"
```

개인 PC의 Chrome/Edge에서 다음 **두 탭**을 엽니다.

| 탭 | 주소 | 할 일 |
|---|---|---|
| Isaac Sim 전체 GUI | [http://127.0.0.1:6080/vnc.html?autoconnect=1&resize=scale](http://127.0.0.1:6080/vnc.html?autoconnect=1&resize=scale) | Franka·블록·트레이, 3D viewport·Stage 확인 |
| 실습 조작 화면 | [http://127.0.0.1:8765](http://127.0.0.1:8765) | 이미지 비교, 사진 촬영·클릭 좌표·모델 지시 |

GUI를 클릭하면 키보드·마우스 입력이 원격 데스크톱으로 전달됩니다. 자동 실행된 시뮬레이션의 Play를 따로 누르지 않습니다. 3D 창에서 관절·물체를 임의로 편집하면 실험 조건이 바뀝니다.

noVNC에 `Connected (unencrypted)`가 보일 수 있습니다. 브라우저와 **개인 PC의 localhost** 구간 표기이며, PC↔Brev 구간은 SSH로 암호화됩니다. 서버의 5901·6080·8765는 localhost에만 열립니다. 이 포트를 `0.0.0.0`이나 인터넷 공개 포트로 바꾸지 마세요.

#### 직접 테스트

1. **5절**의 사진 촬영 → 빨간 블록 윗면 → 트레이 빈 공간 선택 → 수동 집기·배치를 실행합니다. API 없이 로봇 움직임을 확인합니다.
2. **4절**에서 같은 이미지에 대한 두 모델의 원문·좌표를 확인합니다.
3. **6.1절**에서 빨간 블록을 옮기도록 지시합니다.
4. 이후 원하는 6절 실험을 하나씩 실행합니다. 결과는 **Brev 디스크의 `outputs/`**에 저장됩니다.

<a id="brev-scenes"></a>
#### 다른 장면으로 전환

아래 표에서 장면을 선택해 입력합니다. 앞 실험이 끝난 뒤 전환하고, 준비 로그 확인 후 표의 실험 절로 돌아갑니다.

| 입력할 장면 | 이어서 실행할 실험 |
|---|---|
| `blocks` | 5·6.1~6.6 블록 실습 |
| `drawer` | 6.7 서랍 제어 점검·Live 복구 |
| `patrol` | 6.8 Spot 보행 점검·Live 점검 |
| `dual_franka` | 6.9 두 Franka 제어 점검·모델 실험 |
| `transport` | 6.10 자재 운송 제어 점검·모델 실험 |

**실행 위치: Brev 서버 터미널 A · GR-ER2/ · 앞 실험 종료 후 장면 전환**

```bash
read -r -p "장면 (blocks/drawer/patrol/dual_franka/transport): " GR_SCENE
case "$GR_SCENE" in
  blocks|drawer|patrol|dual_franka|transport)
    bash scripts/sim.sh stop
    GR_ER2_SCENE="$GR_SCENE" bash scripts/cloud_gui.sh start
    bash scripts/sim.sh logs
    ;;
  *) echo "장면 이름을 확인하고 다시 입력하세요." ;;
esac
```

`GR_ER2_READY`와 선택한 장면 이름 확인 → Ctrl+C → 해당 실험 명령을 실행합니다. 블록 장면의 로그는 이름 없이 `GR_ER2_READY`만 표시됩니다. GUI·웹·터널은 같은 주소로 유지됩니다. **종료·자료 회수·서버 삭제는 [9.1](#brev-cleanup)**입니다.

## 8. 결과 확인·복사

<a id="read-results"></a>
### 8.1 영상·평가 읽기

브라우저 하단 **저장된 결과 보기 → 최근 실행 목록 새로고침**에서 실행 폴더를 펼치면 입력·원문·평가 파일을 열고 영상을 바로 재생할 수 있습니다. 새 실행 ID의 날짜·시간은 UTC를 사용합니다.

| 폴더 | 자료 |
|---|---|
| `outputs/01_model_comparison/<ID>/input_images/` | 두 모델에 동일하게 전달한 이미지 |

기본·서랍·순찰 실험의 두 원본 영상은 같은 물리 시뮬레이션을 다른 카메라로 기록한 자료입니다. 시뮬레이션 시간 기준 10 FPS로 저장하고 실시간 경과시간은 실행 종류에 따라 `metrics.json` 또는 `recording.json`에 따로 기록합니다. 이 실험들의 `presentation/synchronized.mp4`는 벽시계 시간으로 정렬해 원본과 재생 시간이 다릅니다. 6.9·6.10절 협업 실험은 원본 5 FPS·통합 2.5 FPS를 같은 시뮬레이션 시간축으로 구성합니다. 원본 JPEG 프레임도 보관합니다.

6.1~6.4절의 모델 입력은 판단 시점의 이미지 한 장입니다. 6.5~6.8절의 Live 모델은 최대 1 FPS의 카메라 프레임을 계속 받습니다. 전체 관찰 영상은 10 FPS로 따로 기록하므로 실제 전송 프레임은 `sent_frames/`와 대조합니다.

결과는 **입력 → 호출/보고 → 실제 움직임 → 최종 평가** 순서로 확인합니다. `completed`는 제어 종료, `goal_complete`는 모델 보고, `task_success` 등은 별도 평가입니다. 서랍은 `motion_quality_passed`와 `recovery_success`, Spot은 도착·차단·우회 이벤트·표시등을 함께 봅니다. S2는 복구 전 이미 목적지 안에 있었는지 확인합니다.

### 8.3 결과 복사

영상과 실행 결과는 저장소에 포함되어 있지 않습니다. 실습을 실행하면 `outputs/`에 생성됩니다.

같은 컴퓨터에서 실습하면 해당 GR-ER2 폴더에서 바로 확인합니다. 원격 서버에서 실행했을 때만 아래로 회수합니다. **API 키·실행 대기열은 복사하지 않습니다.**

**실행 위치: 개인 PC · SSH 미접속 · 원격 결과를 받을 때만**

```bash
read -r -p "실습 호스트 SSH 대상: " GR_ER2_HOST
mkdir -p "$HOME/gr-er2-results/outputs" "$HOME/gr-er2-results/samples"
rsync -av "$GR_ER2_HOST:physical-ai-system-design/GR-ER2/outputs/" \
  "$HOME/gr-er2-results/outputs/"
rsync -av "$GR_ER2_HOST:physical-ai-system-design/GR-ER2/data/samples/" \
  "$HOME/gr-er2-results/samples/"
```

원격의 기본 clone 경로를 바꿨다면 콜론 뒤 경로도 바꿉니다. 원본 삭제 옵션은 사용하지 않습니다. 서버를 삭제하기 전 MP4 재생과 평가 JSON을 확인하세요.

## 9. 종료

1. 진행 중인 실험이 끝나고 영상·JSON이 저장됐는지 확인합니다.
2. **웹 서버 터미널 B에서 Ctrl+C**를 누릅니다.
3. 로봇 시뮬레이션을 켰다면 아래 명령을 실행합니다. API 이미지 실습만 했다면 생략합니다.

**실행 위치: 실습 호스트 터미널 A · GR-ER2/ · 로봇 실습 종료**

```bash
bash scripts/sim.sh stop
docker ps --filter name=gr-er2-sim
nvidia-smi
```

`gr-er2-sim`·`gr-er2-sim-gui`가 실행 목록에 없어야 합니다. 이 명령은 전용 컨테이너만 종료하며 코드·API 키·결과·설치본을 유지합니다. 다른 프로그램의 GPU 사용은 남을 수 있습니다.

4. 원격 접속이면 개인 PC의 **터널 C에서 Ctrl+C**를 누르고 브라우저·WebRTC를 닫습니다.
5. Brev는 [9.1](#brev-cleanup)의 자료 회수·삭제까지 진행합니다. 다른 대여 서버는 해당 type의 중지·삭제 정책을 확인합니다. 컨테이너 종료만으로 서버 비용이 멈추지는 않습니다.

다음 실습은 **0.2**부터 시작합니다. 웹의 “정지 요청” 버튼은 로봇 행동을 멈추는 기능입니다. GPU 작업 종료는 위 `sim.sh stop`으로 처리합니다.

<a id="brev-cleanup"></a>
### 9.1 Brev — 결과 회수 후 서버 삭제

검증에 사용한 `massedcompute_L40S`는 **중지·재시작을 지원하지 않습니다.** 실험이 끝나면 결과를 개인 PC로 복사하고 서버를 삭제합니다. 브라우저나 Docker만 종료하면 서버 과금이 계속됩니다.

1. 실험 저장이 끝났는지 확인합니다. Brev 터미널 B의 웹 서버는 Ctrl+C로 종료합니다.
2. Brev 터미널 A에서 GUI·시뮬레이터를 종료합니다.

**실행 위치: Brev 서버 터미널 A · GR-ER2/ · 결과 저장 완료 후**

```bash
bash scripts/cloud_gui.sh stop
docker ps --filter name=gr-er2-sim
nvidia-smi
exit
```

3. 개인 PC의 새 터미널 D에서 결과를 회수합니다. 복사 대상은 `outputs/`와 입력·샘플 `data/`이며, API 키·가상환경·인증 쿠키는 제외합니다.

**실행 위치: 개인 PC · 터미널 D · SSH 미접속 · 결과 회수**

```bash
export PATH="$HOME/.local/share/gr-er2/brev-0.6.335:$PATH"
export BREV_INSTANCE="$(cat "$HOME/.config/gr-er2/brev-instance")"
GR_RESULT_DIR="$HOME/gr-er2-results/$BREV_INSTANCE"
mkdir -p "$GR_RESULT_DIR/outputs" "$GR_RESULT_DIR/data"
rsync -av "$BREV_INSTANCE:physical-ai-system-design/GR-ER2/outputs/" "$GR_RESULT_DIR/outputs/"
rsync -av "$BREV_INSTANCE:physical-ai-system-design/GR-ER2/data/" "$GR_RESULT_DIR/data/"
rsync -rnc --itemize-changes "$BREV_INSTANCE:physical-ai-system-design/GR-ER2/outputs/" "$GR_RESULT_DIR/outputs/"
rsync -rnc --itemize-changes "$BREV_INSTANCE:physical-ai-system-design/GR-ER2/data/" "$GR_RESULT_DIR/data/"
```

마지막 두 검사는 파일 내용을 비교하며 파일을 수정하지 않습니다. 변경 목록이 없어야 합니다. 개인 PC의 `gr-er2-results/<서버이름>/outputs/`에서 MP4 재생과 평가 JSON을 열어 확인하세요. 별도로 작성한 코드가 있다면 그것도 보관합니다. Windows WSL 폴더는 파일 탐색기의 Linux → Ubuntu → home에서 찾습니다.

4. 터널 C에서 Ctrl+C를 누릅니다. 아래에서 **삭제할 서버 이름을 직접 확인**한 후 삭제합니다. 서버 디스크와 그 안의 API 키가 함께 삭제되며, 회수하지 않은 파일은 복구할 수 없습니다.

**실행 위치: 개인 PC · 터미널 D · 복사·재생 확인 후 해당 실습 서버만 삭제**

```bash
brev ls
read -r -p "삭제할 서버 이름을 다시 입력하세요: " GR_DELETE_NAME
if [ -n "$BREV_INSTANCE" ] && [ "$GR_DELETE_NAME" = "$BREV_INSTANCE" ]; then
  brev delete "$BREV_INSTANCE"
else
  echo "이름이 일치하지 않아 삭제하지 않았습니다."
fi
brev ls
```

실습 서버가 목록에서 사라졌는지 확인합니다. 다음에 다시 실습하려면 1.8~1.9로 새 서버를 만들고 본인 키를 등록합니다. 개인 PC로 회수한 결과는 유지됩니다.

## 10. 문제 해결

| 증상 | 해결 순서 |
|---|---|
| `python3.12` 없음 / venv 실패 | 워크스테이션: 1.1 → 1.3. Brev: 1.9 스크립트가 별도 Python 3.12.11을 설치. 이후 `.venv/bin/python` 사용 |
| Python 패키지 충돌 | 전역 pip 설치를 멈추고 프로젝트 `.venv/bin/python` 사용. `pip check`로 확인 |
| Docker permission denied | 1.5의 그룹 추가 후 로그아웃·로그인. 일반 계정 `docker version` 확인 |
| `could not select device driver` / GPU 없음 | 호스트 `nvidia-smi` → 1.6 Toolkit → 1.7 GPU 전달 검사 |
| NGC pull unauthorized | 이미지 태그 확인. 접근 인증이 요구되면 [NGC](https://ngc.nvidia.com/) 계정·약관·레지스트리 키를 준비해 `docker login nvcr.io` 실행. 사용자명 `$oauthtoken`, 비밀번호 칸에 NGC 키를 입력하며 명령 인자로 넣지 않음 |
| 첫 화면이 오래 안 나옴 | `runtime/isaac.log` 확인, asset HTTPS 접근·남은 디스크 점검, `GR_ER2_READY`까지 대기. Brev 첫 GUI는 창 표시 후 장면 준비까지 수 분이 걸릴 수 있음 |
| Brev noVNC 연결 실패 | 7.5 터널 C 유지 → 서버에서 `bash scripts/cloud_gui.sh status` → `runtime/cloud-desktop/` 로그 확인. 인터넷 공개 포트 추가 불필요 |
| Brev `DISPLAY :99` 또는 6080/5901 사용 중 | 본인의 기존 `cloud_gui.sh status` 확인. 같은 프로젝트는 재사용 가능. 다른 작업은 종료하지 말고 별도 서버 사용 |
| Brev Python 갱신 | `bash scripts/setup.sh`가 `runtime/bootstrap-venv/bin/uv`의 Python 3.12.11을 사용. bootstrap 폴더를 삭제했다면 1.9 재실행 |
| 모델 목록 false / 404 | `configs/default.json`과 [공식 모델](https://ai.google.dev/gemini-api/docs/robotics-overview) 확인. 모델 접근을 해결한 뒤 재실행 |
| 403 | 같은 프로젝트의 키인지·키 제한·차단 상태·조직 권한 확인. 2.1의 Gemini 전용 키 제한 적용 |
| 402 | [AI Studio Billing](https://aistudio.google.com/billing)에서 해당 키 프로젝트의 선불 잔액 확인 |
| 429 | 프로젝트 할당량·사용량을 확인하고 대기. 중복 클릭·자동 반복 호출 중지 |
| GUI 키 미등록 / 키 교체 후에도 오류 | 실습 호스트 GR-ER2의 `.env` 확인. 기존 환경변수 키 충돌 확인 후 웹 서버 재시작 |
| 샘플 목록이 비어 있음 | API만 쓰면 내 이미지 업로드. 블록 샘플은 3.1에서 생성 |
| 8765 포트 사용 중 | 기존 본인 웹 서버를 종료하거나 `bash scripts/web.sh --port 8766` 사용. 원격 터널도 `8766:127.0.0.1:8766`, 브라우저도 8766으로 통일 |
| 다른 화면 모드가 실행 중 | 진행 결과 저장 → `sim.sh stop` → 원하는 모드 실행 |
| GUI DISPLAY / 인증 오류 | Xorg 데스크톱 터미널인지 확인. `xauth` 설치와 `XAUTHORITY` 확인. SSH X11 forwarding은 직접 GUI 경로에 포함하지 않음 |
| WebRTC 실패 | LAN/VPN IPv4·TCP 49100·UDP 47998 도달 여부 확인. 웹 카메라 경로로 기본 실습 가능 |
| 로봇 이동 후 물체는 그대로 | `completed`와 실제 배치 성공을 구분. 블록 윗면·목적지 빈 공간을 새 이미지에서 선택 |
| Live 감지가 늦음 | 영상 전송·API 응답·제어 주기는 서로 다름. `sent_frames/`·타임라인·평가에서 감지 시점 확인 |

### 폴더 복사 후 기존 컨테이너가 예전 경로를 참조하는 경우

컨테이너 마운트는 생성할 때 고정됩니다. 스크립트는 현재 프로젝트 경로와 다른 컨테이너를 발견하면 중단합니다. 먼저 마운트를 확인하고, **예전 실험이 종료된 컨테이너만** 이름을 바꿔 보존합니다.

**실행 위치: GPU 실습 호스트 · GR-ER2/ · 마운트 불일치 오류일 때만**

```bash
docker inspect gr-er2-sim --format '{{json .Mounts}}'
docker inspect gr-er2-sim-gui --format '{{json .Mounts}}'
```

없는 컨테이너의 `No such object`는 무시합니다. 아래는 `gr-er2-sim`이 존재하고 **중지 상태**일 때만 실행합니다. GUI 컨테이너라면 이름 두 곳을 `gr-er2-sim-gui`로 바꾸세요. 실행 중인 다른 작업을 자동 종료하지 않습니다.

**실행 위치: GPU 실습 호스트 · 이름과 마운트 확인 후 · 중지된 이전 컨테이너 보존**

```bash
if [ "$(docker inspect -f '{{.State.Running}}' gr-er2-sim)" = false ]; then
  docker rename gr-er2-sim "gr-er2-sim-backup-$(date +%Y%m%d_%H%M%S)"
fi
```

이후 3.1 또는 7절에서 새 컨테이너를 만듭니다. 예전 컨테이너는 삭제하지 않으며 예전 폴더의 결과도 유지됩니다.
